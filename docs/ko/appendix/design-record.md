## 왜 단계로 나눴는가

이 작업의 성격은 이랬다.

```
추론 엔진 내부를 개조한다            <- 막힐 수 있다
새 하드웨어를 산다                   <- 돌려주기 어렵다
운영 중인 서비스를 바꾼다            <- 망가지면 즉시 티가 난다
```

세 위험이 겹치므로, **가장 싸고 가장 되돌리기 쉬운 것부터** 배치했다.

| Phase | 내용 | 비용 | 실패 시 손실 |
|---|---|---|---|
| **0** | 사전 조사 / 양자화 A/B | **0** (카드 불필요, 서비스 무영향) | 시간뿐 |
| 1 | 하드웨어 준비 | 카드 구입 | 15 USD |
| 2 | 엔진 개조 | 시간 | 백업으로 복구 |
| 3 | 오케스트레이터 통합 | 시간 | 백업으로 복구 |
| 4 | 검증 및 전환 | - | 롤백 |

**기존 서비스는 마지막 단계까지 그대로 두었다.** 새 구조가 검증되기 전에 옛 구조를 내리지 않는다.

## Phase 0 - 사전 조사 (카드 불필요, 서비스 무영향)

### 0-1. 엔진 내부 구조 조사 [중요] 가장 먼저

**여기서 막히면 계획 전체가 무너지므로 최우선이었다.** 카드를 사기 전에, 코드를 한 줄 고치기 전에 한다.

확인한 것과 **중단 기준**은 이랬다.

| 확인 | 왜 중요한가 | 중단 기준 |
|---|---|---|
| 조건이 값 타입인가 | 포인터/핸들이면 직렬화 불가 | 핸들이면 **설계 폐기** |
| 조건 생성이 한 곳인가 | 여러 곳이면 개조 범위 폭발 | 흩어져 있으면 재검토 |
| 주입 지점이 명확한가 | 배관 작업량 결정 | - |
| 조건이 배치 전체에 재사용되나 | 아니면 분리 이득 없음 | 매 장 재계산이면 **이득 없음** |
| 다른 확장이 조건을 건드리나 | 건드리면 분리 불가 | 건드리면 재검토 |
| 실제 채워지는 필드가 몇 개인가 | 직렬화 대상 확정 | - |

**전 항목 통과했다.** 특히 마지막이 중요했는데, 조건 구조체에 필드가 10개 넘게 있었지만 실제로 쓰이는 건 **hidden states와 pooled 벡터 2개뿐**이었다. 나머지는 다른 모델 계열용이었다.

> 이 조사가 나중에 **사후 검증**으로 되돌아왔다. 직렬화된 파일 크기가 `4096 x 토큰수 x 4 + 768 x 4 + 헤더` 와 바이트 단위로 일치해서, **파일에 정확히 두 텐서만 들어 있음이 산술로 확인됐다.**

### 0-2. 양자화 A/B - 카드 없이 지금 스택에서

인코더를 8GB 카드에 올리려면 양자화가 필요하다. **그런데 양자화가 품질을 망치면 계획 전체가 무의미하다.** 카드를 사기 전에 지금 스택에서 먼저 확인했다.

```
sd-cli -M convert -m t5xxl_fp16.safetensors -o t5xxl-q8_0.gguf --type q8_0
```

동일 프롬프트/시드/스텝 수로 fp16과 q8_0을 비교했다.

> **아래는 당시 측정한 값 그대로다.** q8_0 의 13.97초는 이후 통제된 재측정에서 **10.09초**(같은 기본 설정)로 나왔다. 이 문서는 설계 과정의 기록이므로 당시 값을 남기되, **현재 유효한 수치는 [부록 7-3](../98-benchmark.md#7-3-왜-cpu-대비-25배인가---연산-강도와-분기점)을 볼 것.**

| 항목 | fp16 | q8_0 | 변화 |
|---|---|---|---|
| CPU 인코딩 | 25.09초 | **13.97초** | -44% |
| 모델 로드 | 7.32초 | 3.83초 | -48% |
| RAM | 9,084MB | **4,826MB** | **-4.26GB** |
| 샘플링 | 1.39 s/it | 1.39 s/it | **동일** |

품질은 **픽셀 평균 차이 0.72/255**, 최대 149였다. 색/구도/소품 배치 같은 의미론적 요소는 유지되고 손가락/얼굴형처럼 **원래 불안정한 영역만** 갈렸다. 임베딩이 미세하게 달라져 확산 궤적이 갈라진 결과다.

**A/B는 반드시 픽셀 단위로 비교한다.** PNG 바이트 비교는 메타데이터 청크 때문에 무조건 다르게 나온다.

```
python3 -c "from PIL import Image; a=Image.open('a.png').tobytes(); b=Image.open('b.png').tobytes(); print('IDENTICAL' if a==b else 'DIFFERENT')"
```

**부수 소득이 있었다.** 양자화는 새 카드 없이도 그 시점 스택에 즉시 이득이었다 - RAM이 절반으로 줄고 CPU 인코딩이 44% 빨라진다. **Phase 1이 실패해도 Phase 0의 산출물은 남는다.** 단계 배치를 이렇게 하면 위험이 줄어든다.

### 0-3. 커널 경로를 소스로 확정 [중요] 카드 불필요

15 USD짜리 카드에 일을 맡기는 근거가 **"INT8 연산이 정상 속도로 돈다"** 였다. 그런데 하드웨어에 기능이 있다는 것과 프레임워크가 그 경로를 쓴다는 것은 **다른 문제다.**

판정 함수를 직접 읽었다.

```c
if (turing_mma_available(cc)) return true;
if (ggml_cuda_highest_compiled_arch(cc) < GGML_CUDA_CC_DP4A) return false;   // 610
if (GGML_CUDA_CC_IS_NVIDIA(cc)) {
    return !fp16_mma_hardware_available(cc) || ne11 < MMQ_DP4A_MAX_BATCH_SIZE;   // 64
}
```

- **P104(sm_61)** - FP16 텐서코어가 없으므로 `!false = true`. **배치 크기와 무관하게 항상 INT8 경로를 탄다**
- **V100(sm_70)** - 텐서코어가 있어 `ne11 < 64` 조건에 걸린다. 512토큰이면 false가 되어 dequant + cuBLAS FP16 경로

**직관과 반대다.** 구세대 카드가 오히려 INT8 경로를 확정적으로 탄다.

**여기서 필수 조건 하나가 나왔다.** `ggml_cuda_highest_compiled_arch(cc) < 610` 이면 INT8 경로가 비활성화된다. 당시 빌드는 `CMAKE_CUDA_ARCHITECTURES=70` 이라 **P104에서는 실행조차 안 되는 상태**였다.

**다만 이건 미리 알아낸 것이 아니다.** 카드를 꽂고 실행이 안 된 뒤에야 확인했고, 빌드를 다시 했다 -> [구축 기록 4-1](build-log.md#4-1-빌드---모든-대상-아키텍처를-넣는다). **소스를 읽는 단계에서 이미 손에 있던 조건인데 빌드 설정과 연결짓지 못했다.**

> **타이밍으로는 이걸 확정할 수 없었다.** 실측 0.33초는 INT8 이론치(109ms)와 FP32 폴백 이론치(393ms) 사이에 있어 구분이 안 된다. **1차 근거는 소스 분석이고 타이밍은 모순 여부를 보는 보조 자료다** -> [No.1 5-2](../01-role-assignment.md#5-2-커널-경로는-타이밍으로-단정할-수-없다)

## Phase 1 - 하드웨어 준비

### 1-1. GPU 지정을 UUID로 전환 [중요] 카드 장착 **전에**

**순서가 중요하다.** 카드를 꽂으면 인덱스가 밀리므로, 밀리기 전에 UUID 기반으로 바꿔 둬야 한다. 실제로 이렇게 밀렸다.

| | 장착 전 | 장착 후 |
|---|---|---|
| V100 32GB (LLM) | index 1 | **index 2** |
| V100 16GB | index 0 | index 3 |
| V100 16GB | index 2 | index 0 |

**인덱스로 지정한 채 꽂았다면 LLM이 16GB 카드에 올라가려다 OOM 났을 것이다.**

### 1-2. 다중 아키텍처 빌드

```
cmake -B build -DCMAKE_BUILD_TYPE=Release -DSD_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES="61;70"
```

설계 초안에서는 **빌드를 둘로 나누려 했다** - 인코더용 `build-p104`(sm_61)와 워커용 `build`(sm_70). 컴파일 시간과 라이브러리 크기가 절반이라는 이유였다.

**실제로는 단일 바이너리로 갔다.** 운영/이력 관리에서 이점이 더 컸다.

| | 단일 바이너리 | 아키텍처별 빌드 |
|---|---|---|
| 설정 | 경로 하나 | 서비스마다 바이너리 지정 |
| 잘못된 바이너리 실행 | 불가능 | **가능 (조용히 실패하거나 느려짐)** |
| 이력 관리 | 커밋 하나 = 상태 하나 | 트리별로 버전이 어긋날 수 있음 |

**"빌드 시간 절반"은 한 번 내는 비용이고, "잘못된 바이너리를 실행할 수 있음"은 계속 남는 위험이다.**

### 1-3. 실측 게이트 [중요]

카드를 꽂고 **가장 먼저 인코딩 시간을 쟀다.** 여기서 기대치가 안 나오면 되돌릴 시점이었다.

웜 상태에서 256토큰 **0.33초**. 당시 CPU 값(13.97초) 대비 42배로 판단해 통과시켰다. **이후 통제된 재측정에서 CPU 최선값이 8.30초로 나와 실제 격차는 25배다** - 판정을 뒤집지는 않았다.

## Phase 2 - 엔진 개조

### 2-1. 직렬화 - 해석하지 않는 것이 핵심

축 규약(row-major냐 프레임워크 고유 순서냐)을 **해석하지 않기로** 했다.

```
shape 벡터와 flat 데이터를 있는 그대로 왕복시킨다
```

의미를 부여하지 않으면 규약이 어느 쪽이든 정확히 복원된다. **축이 뒤집히면 이미지가 조용히 망가지는데 디버깅이 매우 번거롭다.** 해석을 시도했다면 여기서 시간을 크게 잃었을 것이다.

함정 하나가 있었다. `ggml_n_dims()` 는 **뒤쪽 차원의 1을 잘라낸다.** 원래 차원 수를 메타데이터에 따로 기록해야 왕복이 정확하다.

### 2-2. 검증 게이트 [중요] - HTTP보다 CLI 먼저

**이 순서가 이 단계에서 가장 중요한 결정이었다.**

HTTP부터 만들면 이미지가 틀렸을 때 **직렬화/주입/네트워크 중 어디가 문제인지 구분이 안 된다.**

```
1) 정상 생성 + 조건 저장                    -> 이미지 A
2) 텍스트 인코더 인자를 빼고 조건만 주입     -> 이미지 B
3) A 와 B 가 픽셀 단위로 동일한가
```

이 한 번으로 셋이 동시에 증명된다.

- 직렬화 왕복의 정확성
- 주입 지점의 정확성
- **워커가 텍스트 인코더 없이 기동되는지**

세 번째는 사전에 우려가 있었다 - "모델 메타데이터 검증이 인코더 부재를 거부할 수 있다". **통과했다.** 가중치가 lazy 로드라 호출하지 않으면 아예 로드되지 않는다.

> 실제로 이 게이트가 버그를 하나 잡았다. 첫 시도에서 픽셀이 달랐고, 원인은 CPU 백엔드와 GPU 백엔드의 부동소수점 차이였다. **같은 백엔드끼리 비교하도록 조건을 맞추자 완전 일치가 나왔다.** HTTP를 먼저 만들었다면 이 원인에 도달하기까지 훨씬 오래 걸렸을 것이다.

### 2-3. 예상 밖의 수확 - 기동 인자가 아니었다

얼굴 일관성 확장의 ID 임베딩은 **캐릭터를 바꿀 때마다 워커를 전부 재기동해야 하는 것으로 가정**했다. 구조상 기동 인자로 넘기게 되어 있었기 때문이다.

확인해 보니 **엔진 내부에서는 처음부터 요청별 파라미터**였고, 단지 HTTP로 넘길 통로가 없었을 뿐이었다. **코드 두 줄**로 재기동이 사라졌다.

```c
load_if_exists("pulid_id_embedding_path", pulid_id_embedding_path);
load_if_exists("pulid_id_weight", pulid_id_weight);
```

**워커 수 N이 커질수록 재기동 비용은 N배가 된다.** 확장을 전제한 설계에서 이런 항목을 미리 찾는 것의 가치가 여기 있다 -> [No.4 4장](../04-orchestration.md#4-기동-인자가-정말-전역-상태인지-의심할-것)

## Phase 3 - 오케스트레이터 통합

### 3-1. 설계 원칙 - 워커 수 N을 항상 전제

이 단계의 모든 결정은 **"나중에 카드를 더 꽂을 것"** 을 전제로 했다.

| 원칙 | 이유 |
|---|---|
| 워커 수를 상수로 가정하지 않는다 | 목록 길이로만 결정 |
| 워커가 동질하다고 가정하지 않는다 | 성능/VRAM/아키텍처가 다를 수 있음 |
| 인코더는 항상 1벌 | 분리의 전제 |
| **작업 단위를 최소화한다** | 불균형이 1작업으로 제한 |

**1장 = 1작업으로 쪼개면 정적 라운드로빈으로 충분하다.** 배치로 미리 나누면 느린 워커가 전체를 지연시키지만, 1장 단위면 불균형이 최대 1장이다. **이기종 워커가 실제로 생기기 전까지 동적 디스패처는 불필요하다.**

구현은 [`reference/orchestrator.py`](../../../reference/orchestrator.py) 에 일반화해 두었다.

### 3-2. 여기서 가장 많은 시간을 잃었다

통합 직후 **인코딩이 14초에서 56초로 늘어나는** 현상이 있었다. 원인은 세 가지가 연쇄한 것이었다.

```
No.1 오케스트레이터가 생성 직전에 서비스 기동을 요청한다
No.2 그때 아직 모델을 읽는 중이면 "안 떠 있다"고 판정해 두 번째 세트를 띄운다
No.3 첫 세트는 로딩 중이라 SIGTERM 을 늦게 처리해서 안 죽는다
      -> 포트당 프로세스가 2개씩 남아 CPU 와 디스크를 두고 싸운다
```

수정은 둘이었다.

- **기동을 락으로 직렬화** - 로딩 20초 사이의 중복 요청을 막는다
- **종료에 `kill()` 폴백** - `terminate()` 후 타임아웃되면 확실히 죽인다

> 증상이 **"왜 갑자기 느려졌지"** 로 나타나 원인이 프로세스 관리에 있다는 데 도달하기까지 오래 걸렸다. `ps -ef` 로 프로세스 수를 세어 보고서야 알았다. **성능 이상이 보이면 프로세스 개수부터 확인하는 것이 싸다.**

## 되돌아보며 - 무엇이 효과적이었나

### No.1 조사를 가장 앞에 둔 것

Phase 0-1에서 "조건이 값 타입인가"가 아니었다면 계획 전체가 무너졌다. **카드를 산 뒤에 알았다면 15 USD가 아니라 시간을 날렸을 것이다.**

일반화하면 이렇다 - **되돌리기 가장 어려운 결정(하드웨어 구매)을, 가장 싼 확인(소스 읽기) 뒤에 배치한다.**

### No.2 중단 기준을 미리 적어 둔 것

각 단계에 "여기서 이러면 멈춘다"를 미리 써 두면, 막혔을 때 **계속 파고들지 말지를 감정이 아니라 기준으로 판단**할 수 있다.

### No.3 부분 산출물이 남게 배치한 것

Phase 0-2의 양자화는 Phase 1이 실패해도 그 자체로 이득이었다(RAM 절반, 인코딩 44% 단축). **단계를 이렇게 배치하면 중단해도 손실이 0이 아니다.**

### No.4 CLI 검증을 HTTP보다 먼저 한 것

계층을 하나씩 쌓으면서 검증하면 실패 지점이 항상 **마지막에 추가한 계층**으로 좁혀진다. 전부 만들어 놓고 테스트하면 원인 후보가 곱으로 늘어난다.

### 반대로, 놓쳤던 것

**설계 초안의 "8장 92초" 목표는 실제 108초와 어긋났다.** 원인은 기준선에 얼굴 일관성 확장이 빠져 있었기 때문이다. **목표치를 세울 때도 기준선의 조건을 명시했어야 했다.**

그리고 프로세스 관리(3-2)는 설계 문서에 아예 항목이 없었다. **"띄우고 내리는 것"을 사소하게 봤고, 그게 이 프로젝트에서 가장 오래 잡은 버그가 됐다.**
