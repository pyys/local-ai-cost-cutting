## 1. 작업을 구체화하고 상세화한다

본인이 하려는 작업을 구간별로 분해하고, 각 구간의 주요 자원 소모를 확인하는 작업을 가장 먼저 해야 한다.

```
1. 돌려야 할 작업을 전부 나열한다        (LLM 추론 / 이미지 생성 / 인코딩 ...)
2. 각 작업을 구간으로 분해한다            (연산 / 메모리 대역폭 / 통신 / 저장 I/O)
3. 각 구간의 비중을 계산해 병목을 판정한다
4. 후보 GPU를 대입해 "단위 성능당 가격"을 산출한다
5. 분리 가능한 모듈이 있는지 확인한다
```

이걸 먼저 한 뒤에야 필요한 하드웨어 스펙을 산출할 수 있다. 이 작업 없이 하드웨어 구매부터 진행하면 **"싸게 샀는데 쓸 데가 없는 하드웨어"** 나 **"비싸고 오버스펙인 하드웨어"** 가 남는다.

## 2. 병목 판정은 계산으로 확인할 수 있다

> ※ 아래 수치는 이 프로젝트의 모델(Qwen 3.6 27B Q6 / FLUX D Q8)과 GPU(V100 32GB) 기준의 실측 + 추정치다.
> **장비나 작업이 달라지면 비율과 수치가 달라진다.** 절차를 보고 자기 장비 값으로 다시 채워야 한다.

**LLM 추론(디코딩)** - 30 t/s 일 때 토큰 1개당 33.3ms

```
33.3 ms/token ~= 메모리 읽기 27.8ms (84%) + 연산 0.4ms (1%) + 오버헤드 5ms (15%)
```

**이미지 생성(FLUX D)** - 프롬프트 인코딩이 끝난 뒤 1장에 26.9초 (768x768 / 15스텝 / PuLID 활성)

```
26,900 ms/img ~= 메모리 읽기 1,200ms (4%) + 연산 24,300ms (90%) + VAE 1,400ms (5%)
```

> **이 문서의 장당 시간은 모두 PuLID 활성 기준이다.** PuLID(얼굴 일관성 확장)는 스텝당 22%를 더 쓴다(1.39 -> 1.70 s/it). 비활성이면 같은 조건에서 22.2초다. 기준선을 섞으면 개선을 과대/과소평가하게 된다 -> [함정 모음 - 측정/검증](99-pitfalls.md#5-측정검증)

**두 작업을 비교하면 LLM 추론은 전체 시간의 84%를 메모리 읽기에, 이미지 생성은 90%를 연산에 쓴다.** 이 계산을 사전에 하지 않으면, 실제로는 대역폭이 지배하는 LLM을 위해 연산 성능이 높은 GPU에 비용을 지불하는 낭비가 발생할 수 있다.

근거 계산은 이렇다.

| | LLM 디코딩 (토큰 1개) | 디퓨전 (스텝 1회) |
|---|---|---|
| 연산량 | 2 x 27B = **54 GFLOP** | 2 x 12B x 2,560토큰 + 어텐션 = **66,000 GFLOP** |
| 메모리 트래픽 | 21 GB (가중치 전량 1회) | 60.5 GB (Q8 읽기 + fp16 변환/재읽기) |
| 연산량/데이터크기(=연산 강도) | **2.6 FLOP/byte** | **1,091 FLOP/byte** |

> 이 표에는 적용 조건이 붙는다 -> [관련 고지 1)](#관련-고지)

LLM 디코딩은 가중치를 한 번 읽어 토큰 **1개**를 처리하는 반면, 디퓨전은 한 번 읽어 **2,304개의 잠재 패치**를 처리한다. 그 결과 **연산 강도가 420배 벌어지고**(2.6 -> 1,091), 병목이 생기는 지점이 아예 달라진다.

## 3. 일반화 - 루프라인 모델

위 판정은 **카드 스펙 2개와 작업 특성 2개**만으로 일반화할 수 있다. 이 방식을 [**루프라인 모델**(roofline model)](https://en.wikipedia.org/wiki/Roofline_model)이라고 하며, **연산 강도**(arithmetic intensity)와 **분기점**(ridge point) 두 값을 비교해 어느 자원이 상한인지 판정한다.

```
연산 강도(arithmetic intensity) = 작업의 FLOP / 작업의 메모리 트래픽
분기점(ridge point)             = 카드의 연산 성능 / 카드의 메모리 대역폭

연산 강도 < 분기점  ->  메모리 바운드  ->  대역폭 넓은 카드 필요
연산 강도 > 분기점  ->  연산 바운드    ->  연산 강한 카드 필요
```

두 값 모두 `FLOP/byte` 단위로 나온다. **작업 쪽(연산 강도)은 숫자가 클수록 연산 성능에 의존한다는 뜻이고, 카드 쪽(분기점)은 숫자가 클수록 스펙이 메모리보다 연산에 치우쳐 있다는 뜻이다.**

**두 값이 가까울수록 그 작업에 적합한 GPU다.** 크게 벌어지면 남는 쪽 자원이 놀게 된다.

| 카드 | 연산 성능 | 대역폭 | **분기점** |
|---|---|---|---|
| V100 | 125 TFLOPS (텐서 FP16) | 900 GB/s | **139** |
| **P104-100** | **22 TOPS (INT8 DP4A)** | **320 GB/s** | **68.8** |
| CMP 170HX 개조 | 7.7 TFLOPS (텐서 FP16, 봉인) | 1500 GB/s | **5.1** |

| 워크로드 | 연산 강도 | V100 분기점 대비 | 170HX 분기점 대비 | 판정 |
|---|---|---|---|---|
| LLM 디코딩 | 2.6 | 0.019배 | **0.51배** | **170HX가 근접** |
| **텍스트 인코딩 (T5)** | **498** | 3.6배 | 98배 | 연산 바운드 |
| 디퓨전 스텝 | 1,091 | **7.8배** | 214배 | **V100이 근접** |


> **위 판정에는 단서가 붙는다. 표만 보고 결론 내면 안 된다** -> [관련 고지 2)](#관련-고지)

**이 계산은 장비 없이 사전에 가능하다.** 비슷한 가격대에 성격이 전혀 다른 장비가 존재하는 경우가 있으므로, 장비 계획 단계에서 반드시 해야 한다.

※ 예를 들어 V100 32GB는 약 700 USD, CMP 170HX는 약 1,000 USD로 **가격 차이는 170HX 기준 30% 수준**이지만, **페이퍼 스펙상 분기점은 20배 이상 차이난다.**

## 4. 단위 성능당 가격

```
1 단위 성능당 가격 = 카드 가격 / 그 카드에서의 초당 처리량
```

이 프로젝트의 실측 예시 (이미지 생성은 PuLID 활성, 인코딩은 [격리 측정](99-pitfalls.md#5-측정검증) 256토큰 단독 기준):

| 작업 | 카드 | 처리량 | 가격 | 단위 성능당 |
|---|---|---|---|---|
| 이미지 생성 **(1)** | V100 16GB | 26.9초/장 = 0.037 장/s | 200 USD | 약 5,400 USD per (장/s) |
| 이미지 생성 | V100 32GB | 26.9초/장 = 0.037 장/s | 700 USD | 약 18,900 USD per (장/s) |
| 텍스트 인코딩 | V100 16GB | 0.085초/회 = 11.7 회/s | 200 USD | 약 17 USD per (회/s) |
| 텍스트 인코딩 | **P104-100 8GB** | 0.33초/회 = 3.0 회/s | **15 USD** | **약 5 USD per (회/s)** |

> **(1)** 이 행은 [No.2 인코더 분리](02-encoder-separation.md)를 전제한다 -> [관련 고지 3)](#관련-고지)

### 모듈 단위 비교로 끝내면 안 된다

위 표는 모듈 하나만 본 것이다. **시스템 전체로 환산하면 격차가 훨씬 커진다.**

| | 인코딩 시간 | 8장 총 소요 | 이전 대비 절감 | 추가 비용 | **1 USD당 절감** |
|---|---|---|---|---|---|
| CPU (경합 상태) | 24.5초 | 132초 | - | - | - |
| **P104-100 도입** | **0.86초** | **108초** | **23.6초** | **15 USD** | **1.58 초/USD** |
| V100 도입 (가정) | 0.17초 | 107.3초 | 0.69초 | 185 USD 추가 | **0.0037 초/USD** |

**비용 효율이 약 420배 차이난다.** 15 USD로 23.6초를 줄이는 것과 185 USD를 더 써서 0.69초를 줄이는 것은 같은 종류의 결정이 아니다.

### 비교의 축은 두 개다

단위 성능당 가격은 **같은 산출량을 더 싸게** 얻는 쪽만 본다. 실제 구매 결정에는 반대 방향의 축이 하나 더 있다.

```
축 A  동일 산출량 -> 비용을 얼마나 줄이는가
축 B  동일 비용   -> 산출량을 얼마나 늘리는가
```

이 프로젝트에서는 두 축 모두에서 **저비용 카드 혼합이 고비용 카드 1장을 이겼다.** 기준은 V100 32GB 한 장(700 USD)에 이미지 모델을 통째로 올린 구성이고, 8장 생성에 261.7초가 걸렸다.

| 구분 | 구성 | 비용 | 8장 생성 | 장당 |
|---|---|---|---|---|
| *추정* | A100 80GB x1 | *11,000 USD* | *약 110초* | *13.8초* |
| **기준** | V100 32GB x1 | 700 USD | 261.7초 | 32.7초 |
| **A** | V100 16GB x1 + P104 | **215 USD** | 240.7초 | 30.1초 |
| **B** | V100 16GB x2 + P104 | **415 USD** | **134.0초** | 16.8초 |
| *C* | V100 16GB x3 + P104 | *615 USD* | *105~107초* | *13.2초* |

**A가 축 A(동일 산출량), B/C가 축 B(동일 비용)에 해당한다.** A100과 C는 추정치이며, 산출 근거와 발열 스로틀 관련 단서는 [부록 - 벤치마크](98-benchmark.md)에 있다.

**이 결과가 성립하려면 선행 작업이 하나 필요했다.** 200 USD짜리 16GB 카드는 모델이 안 들어가서 애초에 후보가 아니었고, [모듈 분리](02-encoder-separation.md)로 요구 VRAM 하한을 19.1GB에서 13.6GB로 낮춘 뒤에야 선택지가 됐다.

**카드 선택과 작업 분할 사이에는 분명한 선후가 있다 - 나눈 뒤에야 고를 수 있다.** 다만 그렇다고 절차가 한 번에 끝나는 것은 아니어서, **전체 흐름은 여러 번 반복할 이유가 있다** (6장).

## 5. 후보 GPU 참고표

**아래는 공개 스펙 기반 참고값이다.** 개조판/중고는 편차가 크고, **GPU 가격은 작성자의 거주 지역과 문서 작성 시점에 기반하므로 참조용으로만 쓰고 본인 시장 가격으로 반드시 다시 채울 것.**

(2026-08-11 대한민국 기준)

| GPU | 아키텍처 | VRAM | 메모리 대역폭 | FP16 | INT8 DP4A | 가격 (USD) |
|---|---|---|---|---|---|---|
| GTX 1080 (리테일) | Pascal sm_61 | 8GB | ~=320 GB/s | **1/64 봉인** | O ~=22 TOPS | 80 |
| **P104-100** | Pascal sm_61 | 8GB | ~=320 GB/s | **1/64 봉인** | O ~=22 TOPS | **15** |
| **V100 16GB** | Volta sm_70 | 16GB | 900 GB/s | 텐서 1세대 ~=125 TFLOPS | O | **200** |
| **V100 32GB** | Volta sm_70 | 32GB | 900 GB/s | 텐서 1세대 ~=125 TFLOPS | O | **700** |
| RTX 2080 Ti 22GB 개조 | Turing sm_75 | 22GB | 616 GB/s | 텐서 2세대 | O | 350 |
| RTX 3090 | Ampere sm_86 | 24GB | 936 GB/s | 텐서 3세대 ~=142 TFLOPS | O | 800 |
| CMP 170HX 개조 | Ampere sm_80 | 64GB (보고) | ~=1500 GB/s | **텐서 봉인** | ? | 1,000 |
| A100 80GB | Ampere sm_80 | 80GB | ~=2000 GB/s | 텐서 3세대 ~=312 TFLOPS | O | 11,000 |

> **표의 "1/64 봉인"은 공개 스펙이지 실효 성능이 아니다.** 이 프로젝트의 실측에서 P104의 f16은 4.34 TFLOPS로, 스펙에서 추론한 0.095 TFLOPS의 **45배**였다. 텐서코어가 없어 f16을 FP32로 변환해 처리하므로 **봉인이 발동할 기회 자체가 없다.** 스펙표로 카드를 거를 때는 그 경로가 실제로 선택되는지를 함께 확인해야 한다 -> [부록 12-2](98-benchmark.md#12-2-커널-경로---fp16-봉인은-발동하지-않았다)

이와 유사한 표를 만들어 **작업의 최저 요구치를 못 맞추는 카드를 먼저 걸러낸 뒤**(배율이 아니라 통과/탈락 판정이다), 본인 시장의 가격을 넣고 위의 병목 계산과 대조하면 **작업별 최적 카드**가 나온다. [관련 고지 4)](#관련-고지)

이미지 생성 쪽도 동일한 맥락에서 계산하면 아래와 같다.

| | 연산 성능비 | 가격비 | 판정 |
|---|---|---|---|
| A100 80GB 대 V100 32GB | **2.5배** (312 대 125 TFLOPS) | **15.7배** | 비효율 |

**두 작업 모두에서 A100은 성능 2~3배에 가격 15배대다.** 이 계산이 이 프로젝트가 상위 카드를 포기한 근거였고, **장비 없이 스펙만으로 결론이 났다.**

> 이 계산을 공개된 A100 실측치와 대조하지 못한 이유는 [관련 고지 5)](#관련-고지)에 있다.

## 6. 전체 절차 체크리스트

```
0. 작업 분석
   - 돌려야 할 작업을 전부 나열
   - 각 작업을 구간으로 분해 (연산 / 메모리 대역폭 / 통신 / 저장 I/O)
   - 연산 강도와 카드 분기점을 비교해 병목 판정
       ※ 그 작업이 실제로 쓰는 연산 경로로 계산할 것
   - 분리 가능한 모듈이 있는지 확인
   - 관련 자료와 사례 수집

1. 예산과 하드웨어 확정
   - 예산 상한 확정. 넘으면 클라우드 전환까지 재검토
   - 후보 GPU별 "단위 성능당 가격" 산출 -> 작업별 최적 카드 결정
       ※ 모듈 단위가 아니라 시스템 총 소요에서의 기여도로 판단
   - 모든 대상 카드를 덮는 드라이버 브랜치가 존재하는지 확인 (절대 조건)
   - 그 브랜치와 CUDA 버전이 앞으로 얼마나 유지될지 확인
   - 카드별 FP32 / FP16 스칼라 / FP16 텐서 / INT8 성능을 각각 확인
   - PCIe 슬롯/레인, 전원 용량, 보드 BIOS 지원 확인

2. OS/드라이버
   - apt update && apt upgrade 를 먼저 끝낸다
   - 드라이버 설치, nvidia-smi 로 전 카드 인식/이름 확인
   - PCIe 링크 폭/세대도 함께 기록
   - CUDA apt 저장소 등록 시 드라이버 패키지 pinning
   - CUDA 툴킷 설치

3. 빌드
   - CMAKE_CUDA_ARCHITECTURES 에 모든 대상 아키텍처 (따옴표로 감쌀 것)
   - INT8/MMQ 등 커널 판정 조건을 소스에서 확인

4. 역할 배정
   - UUID 수집, 설정에 딕셔너리로 기록
   - 분석의 병목 판정에 따라 작업별 카드 배정
   - 카드가 잘하는 연산 형식에 맞춰 양자화 형식 결정

5. 모듈 분리 (해당하면)
   - 조사 게이트 확인
   - 직렬화/주입 구현 후 CLI로 픽셀 일치 검증
   - HTTP 엔드포인트로 감싸기
   - 오케스트레이터를 최소 작업 단위로 전환

6. 측정
   - 다른 서비스를 정지하고 격리 측정
   - 동일 입력 3회, 1회차는 버리고 2/3회차 사용
   - 기준선의 조건을 명시적으로 기록 (어떤 기능이 켜져 있었는지)
   - 첫 결과까지의 시간과 전체 시간을 분리해 측정
   - 사람 평가가 개입하는 워크플로면 중첩 효과까지 감안
```

측정 단계의 함정은 [함정 모음 - 측정/검증](99-pitfalls.md#5-측정검증)에 따로 정리했다. **이 문서의 수치 신뢰성과 직결되므로 함께 읽는 것을 권한다.**

### 한 번으로 끝나지 않는다

**위 절차를 1회 수행하는 것만으로는 충분하다고 보기 어렵다.** 전체 절차 1,2 단계를 진행하며 관련 자료와 사례를 수집하는 단계에서 새로운 GPU나 솔루션이 발견되는 경우가 반드시라고 해도 좋을 만큼 자주 발생하고, **흐름 뒤쪽의 선택이 앞쪽에 영향을 주는 경우**도 당연히 존재한다.

다만 **이 절차를 반복하는 것 역시 비용이다.** 적당한 수준까지만 반복해야 한다.

## 관련 고지

1) **2장의 연산 강도 표는 모델 자체(PuLID 미적용) 기준이다.** PuLID를 켜면 연산만 22% 늘어 연산 강도가 더 커지므로, 판정(연산 바운드)은 바뀌지 않는다. 디퓨전의 2,560토큰은 잠재 패치 2,304개(768^2 / 16^2)에 텍스트 조건 256토큰을 더한 시퀀스 길이다.

2) **분기점은 그 작업이 실제로 쓰는 연산 경로로 계산해야 한다.** 3장의 분기점 표는 텐서 FP16 기준인데, LLM 디코딩은 배치 1이라 행렬배벡터(GEMV)여서 **텐서 코어를 거의 쓰지 않는다.** 즉 170HX의 실제 적합도는 표의 0.51배보다 더 좋을 수 있다. 170HX 수치 자체가 커뮤니티 보고값이라 검증도 필요하다. 커널 경로 판정은 [No.1 역할 배정 - 성능이 갈리는 지점](01-role-assignment.md#5-이종-gpu에서-성능이-실제로-갈리는-지점) 참조.

3) **(1)** FLUX D Q8을 통째로 올리면 19.1GB라 16GB 카드에 애초에 들어가지 않는다. 인코더를 떼어내 워커가 13.6GB가 된 뒤에야 16GB 카드가 후보가 된다. **"싼 카드로 같은 일을 한다"는 결론은 모듈 분리라는 선행 작업 위에 성립한다.**

4) 문서 정리 시점에서 170HX는 LLM 추론 작업에 V100 32GB보다 적합한 것으로 판정할 수 있지만, **서버 구축 시점에는 이 판단이 불가능할 정도로 가격 변동이 심했고, 개조 작업의 성공률이 100%가 아니었으며, 추후 학습 작업 등을 예정하는 프로젝트 상황을 고려하여 종합한 결과 최종 구성에서는 채택하지 않았다.**

5) 공개된 A100 실측치를 4/5장의 계산과 대조하려 했으나, **프레임워크/모델 변종/해상도/정밀도가 모두 달라 하드웨어 차이만 분리할 수 없었다** -> [부록 11장](98-benchmark.md#11-측정하지-않은-것)
