## 2. GPU 배치

| 함정 | 증상 | 대응 |
|---|---|---|
| GPU 인덱스 지정 | 카드 추가 시 전부 어긋남 | **UUID 사용** |
| 메인 GPU 지정만으로는 부족 | 보조 모듈이 다른 GPU에 얹혀 OOM 유발 | `CUDA_VISIBLE_DEVICES` 로 격리 후 인덱스 0 지정 |
| PCIe 레인 확인 누락 | 기동 시 모델 로드가 예상의 10배 | `pcie.link.width/gen` 을 미리 확인 |
| **네트워크 인터페이스 이름** | 카드 교체 후 **SSH 불가** | **MAC 주소로 고정** (아래) |

두 번째 항목의 실제 사례: llama.cpp에서 `-mg 1` 로 메인 GPU만 지정했더니 **비전 프로젝터(mmproj)가 GPU0에 1.4GB 얹혀** 나중에 이미지 생성 서버가 OOM 났다. `CUDA_VISIBLE_DEVICES` 로 카드 하나만 보이게 한 뒤 `-mg 0` 을 주는 것이 확실하다.

### 위치 기반 식별자는 전부 같은 함정이다

네 번째 항목이 가장 위험하다. **GPU를 꽂았을 뿐인데 서버에 접속이 안 된다.**

원인은 첫 항목과 완전히 같다 - **PCI 위치를 기준으로 식별자를 붙이면 하드웨어 구성이 바뀔 때 식별자가 바뀐다.** 리눅스의 네트워크 인터페이스 이름(`enp2s0`)도 PCI 슬롯 위치에서 유도되므로, 카드를 추가하면 이름이 바뀌고 그 이름으로 고정해 둔 설정이 어긋난다.

| | 위치 기반 (바뀜) | 고유값 기반 (안 바뀜) |
|---|---|---|
| GPU | `CUDA_VISIBLE_DEVICES=0` | **UUID** |
| 네트워크 인터페이스 | `enp2s0` | **MAC 주소** |
| 블록 장치 | `/dev/sda` | **UUID / PARTUUID** |

**헤드리스 서버라면 순서가 중요하다.** GPU 설정이 틀리면 서비스가 안 뜨는 데서 끝나지만, **네트워크 이름이 어긋나면 하드웨어 변경을 되돌리거나 최악의 경우 OS를 다시 깔아야 할 수도 있다.** 하드웨어를 변경하기 전에 세 가지를 모두 고유값 기반으로 바꿔 두고, 그중 네트워크를 가장 먼저 한다 -> [No.4 1-1](04-orchestration.md#1-1-pci-장비-구성이-바뀌면-gpu-밖에서도-문제가-생긴다)

## 3. 추론 엔진

| 함정 | 증상 | 대응 |
|---|---|---|
| VAE 디코드 컴퓨트 버퍼 | 3744MB 요구로 OOM | 타일링 (416MB, 비용 1.4초) |
| distilled 모델에 CFG 적용 | 3.3배 느려짐 | CFG 스케일 1.0 |
| `--mmap` | 모델 로드 8초 -> 110초 | 쓰지 않음. RAM 절약보다 손해가 큼 |
| 인자 이름 추측 | 서버가 usage만 출력하고 종료 | `--help` 확인 (`--host`가 아니라 `--listen-ip` 등) |
| LoRA 디렉터리 기본값 `.` | 요청마다 재귀 스캔, 루트에서 띄우면 크래시 | 빈 디렉터리 명시 |
| 얼굴 임베딩 추출 (InsightFace) | 구세대 GPU 미지원으로 CUBLAS 실패 | CPU로 추출 |

**`--mmap` 은 직관과 반대다.** RAM을 아껴 준다고 켰다가 모델 로드가 14배 느려졌다. 여러 프로세스가 같은 가중치를 공유하는 상황이 아니라면 손해다.

**LoRA 디렉터리 기본값** 은 서버를 `/` 에서 띄웠을 때 루트 전체를 재귀 스캔하다가 심볼릭 링크에서 터졌다. 요청마다 스캔하므로 반드시 빈 디렉터리를 명시해야 한다.

```
{"error":"server_error","message":"filesystem error: status: Too many levels of symbolic links [./run/udev/watch/22]"}
```

## 4. 프로세스 관리

| 함정 | 증상 | 대응 |
|---|---|---|
| `terminate()` 후 짧은 대기 | 모델 로딩 중(20초+) SIGTERM이 늦게 처리되어 **프로세스가 살아남음** | 타임아웃 후 `kill()` 폴백 |
| 기동 중 재기동 요청 | "안 떠 있음"으로 판정해 **중복 세트 기동** | 락으로 직렬화 |
| 중복 인코더 | CPU/디스크 경합으로 인코딩 14초 -> 56초 | 위 둘로 해결 |
| **`pgrep -f` 를 셸 경유로 실행** | 항상 "살아 있음"으로 오판 | **리스트 형태로 실행** (아래) |

세 항목이 연쇄로 일어났다. 오케스트레이터가 생성 직전에 서비스 기동을 요청하는데, 그때 아직 모델을 읽는 중이면 "안 떠 있다"고 판정해 두 번째 세트를 띄운다. 그런데 첫 세트는 로딩 중이라 SIGTERM을 늦게 처리해서 안 죽는다. 결과적으로 **포트당 프로세스가 2개씩** 남아 CPU를 두고 싸웠다.

### `pgrep -f` 는 자기 자신을 매칭한다

프로세스 정리 로직을 셸 경유로 실행하면 조용히 망가진다.

```python
subprocess.run("pgrep -f sd-server", shell=True)   # X 항상 발견됨
subprocess.run(["pgrep", "-f", "sd-server"])       # O
```

`shell=True` 는 `/bin/sh -c pgrep -f sd-server` 를 띄우는데, **이 래퍼 셸의 명령줄에 검색어가 들어 있다.** `pgrep` 은 자기 PID만 제외하고 부모 셸은 제외하지 않으므로, 대상 프로세스가 하나도 없어도 항상 "살아 있음"이 된다.

같은 이유로 확인용 일회성 명령도 오탐을 만든다.

```
python3 -c "... 'sd-server' ..."     # 이 python3 의 명령줄에도 검색어가 있다
```

**이 프로젝트에서는 이 한 줄 때문에 벤치마크 24회가 전부 즉시 실패했다.** 파생 원칙 하나가 여기서 나온다 - **무인 실행(nohup)에 넣기 전에 정리/방어 로직을 최소 1회는 실제로 태워 볼 것.** 검증되지 않은 방어 코드는 방어하지 않는다.

## 5. 측정/검증

**이 분류는 다른 문서의 수치 신뢰성과 직결된다.** [병목 판정](00-method.md#2-병목-판정은-계산으로-확인할-수-있다)과 [부록 - 벤치마크](98-benchmark.md)를 읽기 전에 함께 보는 것을 권한다.

### 격리 실측 - 카드를 비교하는 유일한 방법

카드 간 비교는 **조건을 맞춘 격리 측정**으로만 의미가 있다. 실사용 로그에서 뽑은 값은 프롬프트 길이와 시스템 부하가 섞여 있어 대략적 참조는 되지만 정밀 비교와는 거리가 멀다.

```
1. 다른 서비스를 전부 정지한다 (워커/LLM 포함)
2. 대상만 단독 기동
3. 동일 입력으로 3회 요청
4. 1회차는 버리고 2/3회차를 쓴다   <- 1회차에는 가중치 로드가 섞인다
5. 카드를 바꿔 반복
```

이 방법으로 얻은 수치는 [부록 7-2](98-benchmark.md#7-2-카드별-인코딩-성능---격리-실측)에 있다. 아래 두 사례가 이 절차가 필요한 이유다.

| 함정 | 증상 | 대응 |
|---|---|---|
| PNG 바이트 비교 | 메타데이터 청크 때문에 항상 다름 | 픽셀만 비교 |
| CPU/GPU 결과 비교 | 부동소수점 커널 차이로 이미지가 미세하게 달라짐 | 버그 아님. 평균 0.72/255 수준. **백엔드를 바꾸면 같은 시드라도 재현 안 됨** |
| 로그의 메모리 예상치 | 실제 할당과 다름 | `nvidia-smi` 로 확인 |
| **콜드 측정끼리 비교** | 로드 시간 비중이 카드마다 달라 **배율이 왜곡됨** (2.3배 vs 실제 3.9배) | **웜 상태로 2회 이상 측정** |
| **페이지 캐시** | 먼저 실행한 쪽만 디스크를 읽어 느려 보임 | 구간 분리 로그 활용, 순서 바꿔 재측정 |
| **타이밍으로 커널 경로 단정** | 다른 경로도 비슷한 값이 나올 수 있음 | **소스의 판정 함수를 직접 확인** |
| 실사용 로그로 카드 비교 | 프롬프트 길이/시스템 부하가 섞임 (0.33초 vs 0.86초) | **조건을 맞춘 격리 측정** |
| **같은 스펙 카드를 동일하다고 가정** | 냉각 조건 차이로 지속 성능이 12% 갈림 | **부하 중 `clocks.sm`/온도를 함께 기록** |

### 실제로 잘못된 결론을 낼 뻔한 사례

**콜드끼리 비교** - 두 카드의 첫 실행 시간을 나눠 "3.9배 차이"라고 추정했는데, 우연히 맞았을 뿐 근거는 부실했다. 두 값 모두 가중치 로드가 섞여 있었고 그 비중이 카드마다 완전히 달랐다(x16 Gen3 vs x4 Gen1). 웜 측정으로 다시 재니 콜드끼리의 비율은 2.3배로 나왔다 - **실제 연산 성능비 3.9배와 어긋난다.**

**페이지 캐시** - 디스크 read 시간이 V100 1.81초, P104 0.15초로 나와 P104가 12배 빨라 보였다. V100 테스트를 먼저 돌려 디스크에서 읽었고 P104는 캐시에 올라온 파일을 읽었을 뿐이었다. **실행 순서의 산물이지 카드 특성이 아니다.**

**구간 분리 로그가 이 둘을 걸러냈다.** `read` / `copy_to_backend` 가 나뉘어 있어서 디스크와 PCIe를 분리할 수 있었다. 로그가 총 시간만 찍었다면 두 오류를 모두 놓쳤을 것이다.

### 같은 스펙의 카드라도 지속 성능은 갈린다

비용 벤치마크에서 **V100 32GB가 V100 16GB보다 장당 12% 느리게** 나왔다. 대역폭도 폼팩터도 최대 클럭도 같은 카드였다.

원인은 **발열 스로틀**이었다. 부하 중 32GB 카드는 82~83C에서 **1,155~1,207 MHz**로 돌았다 - 부스트(1,530)의 78%로, 베이스 클럭(1,290)에도 못 미친다. 전력은 300W 한도에 100W 가까이 남아 있었으므로 전력 캡이 아니다. **그 카드가 섀시 안에서 더 나쁜 자리에 있었을 뿐이다.**

| 증상 | 의미 |
|---|---|
| 콜드에서는 차이가 작은데 **지속 부하에서 벌어진다** | 발열 스로틀의 전형적 신호 |
| 총 소요 시간만 기록했다 | 원인 귀속 불가 |

```
nvidia-smi --query-gpu=index,name,clocks.sm,clocks.max.sm,power.draw,power.limit,temperature.gpu --format=csv -l 5
```

> **다중 GPU 벤치마크에서는 부하 중 `clocks.sm` 과 `temperature.gpu` 를 함께 기록하라.** 총 소요 시간만 보면 절대 보이지 않는다. **같은 모델명/같은 폼팩터라도 성능이 같다고 가정하지 말 것.**

**이 함정이 특히 위험한 이유는 잘못된 결론이 그럴듯하기 때문이다.** 12% 격차를 "모듈 분리 덕분"이라고 적었다면 그 문장은 검증되지 않은 채 남았을 것이고, 다른 사람이 같은 구조를 만들어도 재현되지 않았을 것이다. **가설을 하나씩 소거하는 조건을 추가로 설계하지 않았다면 끝까지 몰랐을 일이다.** 소거 과정 전체는 [부록 9장](98-benchmark.md#9-반증---32gb-카드가-느렸던-이유)에 있다.

#### 파생 - 카드가 늘면 서로를 가열한다

이 측정에서 32GB 카드가 82C일 때 나머지 16GB 카드들은 **39C로 유휴 상태**였다. 즉 각 조건의 실측값은 **"그 카드만 뜨거운" 상황**의 값이다.

워커를 3장/4장으로 늘리면 카드들이 서로를 가열하므로 **각 카드의 지속 클럭이 이 측정보다 낮아진다.** [조건 5 산출값](98-benchmark.md#4-2-조건-5-산출)을 낙관적 상한으로 취급해야 하는 이유 중 하나다.

**확장 계획을 세울 때는 에어플로를 성능 변수로 취급해야 한다.** 카드를 추가하면 추가한 카드의 성능만 얻는 것이 아니라, **기존 카드의 성능도 함께 내려간다.**

## 7. 통념이 틀리는 지점

그럴듯해 보이는 전제가 실측에서 뒤집힌 사례들이다.

### 싼 카드를 먼저 고르지 말 것

**싼 카드를 찾는 것이 아니라, 그 카드에 맡길 자리를 먼저 찾는 것이 순서다.** 카드를 먼저 사고 쓸 곳을 찾으면 실패한다.

이 프로젝트에서 15 USD짜리 카드가 성립한 것은 **텍스트 인코딩이라는 자리가 그 카드에 들어갔기 때문**이다. 조건은 둘이었다 - **모듈이 들어갈 VRAM이 있는가, 그리고 싼가.** 인코딩은 CPU에서 GPU로 옮기는 것만으로 이미 큰 이득이 나는 연산이라, 특정 연산 경로가 살아 있어야 성립하는 종류의 선택이 아니었다.

**뒤집어 말하면 "들어가지 않으면" 아무리 싸도 후보가 아니다.** 인코더가 5.2GB였기에 8GB 카드가 검토 대상이 됐다 -> [No.1 5-3](01-role-assignment.md#5-3-싸고-적재만-되면-된다)

### 연산 바운드라고 SMT를 끄지 말 것

실행 유닛이 포화됐을 것으로 짐작해 물리 코어 수만 쓰면 손해를 볼 수 있다. 이 프로젝트에서 물리 8코어인 CPU 인코딩을 논리 스레드 전부로 돌리자 **22% 빨라졌다.**

| 설정 | 256토큰 인코딩 소요시간 |
|---|---|
| 물리 8코어 | 10.14초 |
| **논리 16스레드 (SMT)** | **8.30초** |
| 엔진 기본값 (`-t` 미지정) | 10.09초 - **물리 코어 수였다** |

원인은 명령 의존 사슬로 보인다. 이 CPU(Zen 2)에는 AVX512-VNNI가 없어 ggml의 INT8 경로가 `maddubs -> madd -> 누산` 을 거치는데, **그 사이의 파이프라인 버블을 SMT가 채운다.**

> **"연산 바운드"는 어느 자원이 상한인지를 말할 뿐, 그 자원의 활용률까지 보장하지 않는다.** 루프라인 판정과 실제 유닛 포화는 별개다.

**엔진 기본값이 물리 코어 수인 경우가 있으므로 `-t` 로 명시해 볼 가치가 있다. 짐작하지 말고 재라.** 계산 근거는 [부록 7-3](98-benchmark.md#7-3-왜-cpu-대비-25배인가---연산-강도와-분기점)에 있다.

### 하드웨어를 샀다고 그 기능을 쓰는 것은 아니다

이 프로젝트는 재구성 전에 **NVLink 보드를 구입해 V100 32GB 2장을 한 달간 운용했다.** 그리고 그 링크를 **한 번도 쓰지 않았다.**

멀티 GPU 적재 명령을 만들었지만 `--split-mode row` 가 빠져 있었고, llama.cpp의 기본값은 레이어 분할이므로 **카드가 두 장 보여도 텐서 병렬로 동작하지 않았다.** 이 사실은 한참 뒤에야 확인했다.

**기능이 켜졌는지는 스펙이 아니라 실행 인자와 로그로 확인해야 한다.** 하드웨어를 갖추는 것과 그 대역폭을 실제로 쓰는 것은 별개다 -> [부록 - 구축 기록 관련 고지 1)](appendix/build-log.md#관련-고지)

> [No.1 5-2](01-role-assignment.md#5-2-커널-경로는-타이밍으로-단정할-수-없다)의 커널 경로 문제와 같은 결이다. **어느 경로가 실제로 선택됐는지는 확인해야 알 수 있다.**

## 8. CPU 바운드 작업도 GPU 측정을 오염시킨다

오케스트레이터는 CPU에서 돌지만, **CPU는 공유 자원이라 GPU 측정에 영향을 준다.**

| 사례 | 영향 |
|---|---|
| 인코딩 단독 16.51초 -> 경합 시 **24.5초** | LLM 서버 + 워커와 CPU 경합 (512토큰) |
| 인코더 중복 기동 -> 14초 -> **56초** | CPU/디스크 경합 |
| 웜 인코딩 0.33초(격리) -> **0.86초**(실사용) | 일부가 CPU 오버헤드 + 청크 수 |

**"CPU 작업이니 무시해도 된다"가 아니라 "CPU 경합이 GPU 측정을 오염시킨다"** 로 다뤄야 한다. 5장의 격리 측정 방법론이 이 이유로 존재한다.

## 9. AI 코딩 도구에 작업을 맡길 때

이 프로젝트의 구축과 문서화는 대부분 Claude Code를 통해 진행했다. 생산성 이득은 컸지만, **도구가 지시하지 않은 파일을 건드리는 일이 실제로 일어났다.**

2026년 8월 21일, 문서를 수정하기 전 백업을 만드는 과정에서 **도구가 기존 과거본의 번호를 확인하지 않고 이미 존재하는 백업 파일에 덮어썼다.** 그 시점의 중간본 하나가 사라졌고, 저장소에 버전 관리가 걸려 있지 않아 복구하지 못했다.

**피해가 한 파일에서 끝난 것은 이력 형태의 백업을 쓰고 있었기 때문이다.** 이 저장소는 문서를 고칠 때마다 직전본을 `_old_N` 으로 남기는 규칙을 지키고 있었고, 덮어쓰인 것은 그 사본 중 하나였다. **본문은 그대로였고, 다른 시점의 사본도 그대로 남았다.**

**같은 사고가 본문에서 일어났다면 결과는 전혀 달랐을 것이다.** 되돌릴 지점이 없으면 그 문서는 통째로 사라진다. 도구가 파일을 쓸 수 있는 환경에서는 다음 셋 중 하나는 반드시 갖춰야 한다.

- **버전 관리** - git 저장소로 두면 어떤 덮어쓰기도 되돌릴 수 있다. 가장 확실하다
- **이력 백업** - 수정 시점마다 사본을 남긴다. 이 프로젝트가 쓴 방법이다
- **쓰기 권한 제한** - 도구가 건드릴 수 있는 경로를 좁힌다

**도구의 출력만 검토하고 도구의 행위는 검토하지 않는 것이 함정이다.** 무엇을 썼는지는 사람이 읽지만, 무엇을 덮어썼는지는 대개 아무도 보지 않는다.
