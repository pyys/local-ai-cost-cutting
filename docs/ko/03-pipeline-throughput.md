# No.3 조기 표시 - 사람이 포함된 파이프라인의 처리량

> 생성 결과를 **완성되는 대로 한 장씩** 내보내면, 사람의 평가 시간과 기계의 생성 시간이 겹쳐
> 전체 소요가 `N x T` 에서 `T` 로 줄어든다.
> **GPU 구성과 무관하다.** 사람이 결과를 골라야 하는 모든 생성 워크플로에 적용된다.

## 1. 생성형 워크플로에서 사람은 병목이다

이 프로젝트에서 이미지를 생성한 결과에는 거의 항상 결함이 있다. 쓸 만한 것을 고르려면 **사람이 평가해야 한다.**

여러 후보 중 나은 것을 골라 그것을 씨앗으로 다시 생성하는 이 방식은 **대화형 진화 연산(Interactive Evolutionary Computation, IEC)** 이라 불린다. 일반 진화 알고리즘은 적합도를 수식으로 계산하지만, 미적 판단처럼 수식화가 어려운 영역에서는 **사람이 적합도 함수(fitness function) 역할**을 한다.

| IEC 개념 | 이미지 생성에서의 대응 |
|---|---|
| 개체군 (population) | 한 번에 생성하는 N장 |
| 선택 (selection) | 마음에 드는 이미지 선택 |
| 돌연변이 (mutation) | img2img 변형 강도 |
| 세대 반복 (generation) | 선택한 이미지를 기준으로 재생성 |

이 구조에서 **사람의 평가 시간은 무시할 수 없는 비용**이다. 한 장 평가에 T초가 걸리면, N장을 모두 받아든 뒤 `N x T` 가 소요된다.

그런데 구현 방식을 잘못 설계하면 이 비용을 **생성이 전부 끝난 뒤에** 지불하게 만든다.

---

## 2. 시간 모델

**생성에 드는 시간이 같다고 놓고, 표시 방식만 바꿨을 때의 차이다.** 생성 총 소요를 G, 첫 장까지를 F, 장당 평가 시간을 T라 하면:

```
일괄 표시 : [생성 G] ----------------------------> [평가 N x T]
            총 = G + (N x T)

1장씩 표시: [첫 장 F] [ 생성 계속 ---------------------- ]
                     [평가][평가][평가]...
            총 ~= G + T          (평가가 생성 간격보다 빠른 경우)
```

**작업 종료 시점이 `G + (N x T)` 에서 `G + T` 로 줄어든다.** 생성 시간 G는 그대로이고, **줄어드는 것은 사람의 평가 시간이 차지하던 자리다.**

기계가 두 번째 이미지를 만드는 동안 사람이 첫 이미지를 평가하기 때문이다. 마지막 한 장의 평가만 겹칠 대상이 없어 남는다.

하이퍼스레딩이 유휴 실행 유닛을 채우는 것과 같은 원리이고, 여기서 채우는 유휴 자원은 **사람의 대기 시간**이다.

> 평가가 생성보다 느리면(T가 생성 간격보다 크면) 역전되어 평가가 지배한다. 그 경우에도 총 소요는 `F + (N x T)` 로, 일괄 표시의 `G + (N x T)` 보다 작다. **F < G 인 한 어느 쪽이든 손해는 없다.**

> **T는 이 프로젝트에서 측정하지 않았다.** 사람의 평가 시간은 작업/숙련도/피로도에 따라 크게 달라지므로, 위 모델은 **T를 미지수로 둔 구조 비교**로 읽어야 한다. 아래 4장의 실측은 G와 F만 다룬다.

## 3. 구현 조건 - 작업 단위를 쪼갤 수 있어야 한다

이 설계가 성립하려면 전체 작업 구조가 **N개의 독립 작업으로 나눌 수 있어야** 한다. 작업구조에서 결과물 도출이 배치로 묶여 있으면 전부 끝날 때까지 아무것도 못 내보낸다.

이미지 생성에서 배치로 묶는 이유는 보통 **프롬프트 인코딩 비용을 1회로 줄이기 위해서**다. 일반적으로는 이미지 1장씩 내보내게 하려면 작업을 배치로 묶지 않고 매 장마다 인코딩을 다시 해야 한다.

이 프로젝트에서는 [인코더를 분리](02-encoder-separation.md)해 조건 텐서를 워커들이 공유하게 만들어 놓은 구조이기 때문에 이 제약이 존재하지 않는다. 

**인코더 분리 없이도 가능하긴 하다.** 장당 재인코딩 비용을 감수하면 된다. 이 프로젝트의 P104 인코딩 기준으로 그 비용은 장당 0.86초이므로, 8장이면 **약 6초**가 추가된다 - 총 소요의 **6% 이내**다.

다만 **인코딩 자원 소모가 큰 구조라면 지불하기 어려운 비용이다.** 이 프로젝트에서도 인코딩을 CPU로 하던 조건이 여기 해당한다. 장당 8.30초씩 7번이면 **58초**가 추가되어, 전체 소요가 4분의 1 가까이 늘어난다. 장당 인코딩을 감수하는 것은 **인코딩이 싼 환경에서만 이득이 성립한다.**

부수 효과로 **인코더 분리시 워커가 2개 이상일 때 부하 분산도 단순해진다.** 1장 = 1작업이면 워커 간 불균형이 최대 1작업으로 제한되어, 정적 라운드로빈만으로도 충분하다. 배치로 미리 나누면 느린 워커가 전체를 지연시킨다.

## 4. 실측

**같은 자원에서 작업 할당 방식만 바꿔 측정했다.** 카드, 인코더 위치, 워커 수가 모두 같고 배치를 낱장으로 쪼갠 것만 다르다.

| | 일괄 표시 (배치) | 1장씩 표시 (낱장) |
|---|---|---|
| **첫 장 표시까지 소요시간 (F)** | **261.5초** | **46.7초** |
| 8장 전체 완료 시간 (G) | 261.7초 | 262.4초 |

**배치로 묶인 작업은 `F = G` 다.** 배치는 8장이 전부 끝날 때까지 아무것도 내보내지 않으므로 전체 작업이 종료되어야 첫 장의 검수를 시작할 수 있다.

낱장 단위로 분할된 작업은 46.7초 만에 첫 장이 산출되었고, 검수는 이 시점에서 시작된다.

※ 이 실험에서 인코더는 V100 VRAM에 있어 **인코딩 1회가 0.17초**에 그쳤기에 낱장 작업이 인코딩을 7회 더 수행했어도 그 비용이 **총 소요의 오차범위 안쪽**이었다. 3장에서 말한 "지불 가능한 비용"의 실측값이 이것이다. 만약 인코더가 더 느린 GPU (ex:P104라면 7회 약 6초)나 CPU(ex: EPYC 7232P 라면 7회 약 58초)에 있었다면, 이 비용은 크게 달라졌을 것이다.

측정 조건과 원시 기록은 [부록 8장](98-benchmark.md#8-해석---작업을-쪼개는-비용)에 있다.

**사용자가 체감하는 것은 전체 시간이 아니라 첫 결과가 나오기까지의 대기다.** 그리고 2장에서 봤듯 이건 체감만의 문제가 아니라 실제 총 소요를 줄인다.

## 5. 적용 조건과 한계

**적용되는 조건**

| 조건 | 설명 |
|---|---|
| 결과가 여러 개 생성된다 | N >= 2 |
| **사람이 골라야 한다** | 자동 채점이 가능하면 이 논의가 필요 없다 |
| 결과 간 순서가 무관하다 | 먼저 나온 것부터 평가할 수 있어야 한다 |
| 작업을 쪼갤 수 있다 | 3장의 조건 |



**적용되지 않는 경우**

- **자동 평가가 가능한 워크플로** - 사람이 개입하지 않으면 겹칠 유휴 시간이 없다
- **결과 전체를 봐야 판단이 되는 경우** - 예: 모든 N 간에 비교가 반드시 필요하면 전부 나와야 한다
- **생성이 사람 평가보다 훨씬 빠른 경우** - 겹칠 여지가 작다. 다만 손해도 없다
- **단일 결과만 만드는 경우** - N = 1

**적용 범위는 이미지 생성에 국한되지 않는다.** 사람이 후보 중에서 고르는 구조라면 코드 생성, 문장 초안, 디자인 시안, 음성 합성 등 어디서나 같은 논리가 성립한다.

---

## 6. 설계 원칙으로 정리하면

> **사람이 파이프라인의 일부라면, 사람의 대기 시간도 자원이다.**
> 작업 단위를 쪼개 기계 시간과 사람 시간을 겹치게 하라.

이는 UX 개선이 아니라 **처리량 개선**이다. "로딩 바를 보여주면 덜 답답하다"와는 층위가 다르다 - 실제로 총 소요 시간이 줄어든다.

그리고 이 원칙은 [작업 단위를 최소화하라](04-orchestration.md#2-워커-확장을-전제로-짠다)는 오케스트레이션 원칙과 같은 결론에 도달한다. 부하 분산과 사람 시간 중첩이라는 서로 다른 이유가 **같은 설계**를 가리킨다.
