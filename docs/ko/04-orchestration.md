## 1. GPU 할당은 반드시 UUID로 지정한다

**여러 PCIe 장비를 쓰는 환경에서는 장비 수가 바뀌면 인덱스가 밀리는 일이 대단히 흔하다.** 이 프로젝트에서 인코더 카드를 꽂았을 때도 그랬다.

| | 장착 전 | 장착 후 |
|---|---|---|
| V100 32GB (LLM) | index 1 | **index 2** |
| V100 16GB | index 0 | index 3 |
| V100 16GB | index 2 | index 0 |
| P104 8GB | - | index 1 |

인덱스로 지정했다면 P104 장착 후 기동에서 LLM이 16GB 카드에 올라가려다 OOM 났을 것이다. **UUID는 카드 고유값이라 물리적 재배치와 무관하다.**

```
CUDA_VISIBLE_DEVICES=GPU-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

설정 파일에는 UUID 딕셔너리를 두고 **이름으로 참조**할 수 있다. 이 경우 카드를 늘려도 항목만 추가하면 된다.

**메인 GPU를 지정하는 옵션만으로는 부족하다.** 이 프로젝트에서 llama.cpp에 `-mg 1` 로 메인 GPU를 지정했더니 **비전 프로젝터(mmproj)가 GPU0에 1.4GB 얹혀** 나중에 이미지 생성 서버가 OOM 났다. `CUDA_VISIBLE_DEVICES` 로 카드 하나만 보이게 한 뒤 인덱스 0을 주는 것이 확실하다.

### 1-1. PCI 장비 구성이 바뀌면 GPU 밖에서도 문제가 생긴다

**이건 GPU만의 문제가 아니다.** 근본 원인은 이렇게 일반화된다.

> **PCI 위치를 기준으로 식별자를 붙이면, 하드웨어 구성이 바뀔 때 식별자가 바뀐다.**

같은 원인이 전혀 다른 증상으로 나타나는 대표적인 예가 **네트워크 인터페이스 이름**이다. 리눅스의 Predictable Network Interface Names 정책은 인터페이스 이름을 **PCI 슬롯 위치에서 유도**한다(`enp2s0` 의 `p2s0` 이 그것이다). 그래서 카드를 추가하거나 슬롯을 바꾸면 **이름이 바뀌고, 그 이름으로 고정해 둔 네트워크 설정이 통째로 어긋난다.**

**헤드리스 서버에서는 이게 치명적이다.** GPU를 꽂았을 뿐인데 SSH가 안 되고, 화면도 없어서 원인을 볼 수 없다. 이 프로젝트에서도 카드를 교체한 뒤 실제로 겪었다.

| | 위치 기반 (바뀜) | 고유값 기반 (안 바뀜) |
|---|---|---|
| GPU | `CUDA_VISIBLE_DEVICES=0` | **UUID** |
| 네트워크 인터페이스 | `enp2s0` | **MAC 주소** |
| 블록 장치 | `/dev/sda` | **UUID / PARTUUID** |

네트워크 쪽 대응은 `.link` 파일로 MAC 주소에 이름을 고정하는 것이다.

```
/etc/systemd/network/10-nicname.link      <- [Match] MACAddress= / [Link] Name=
```

**하드웨어를 변경하기 전에 이 세 가지를 모두 고유값 기반으로 바꿔 두는 것이 안전하다.** 특히 원격 접속만 가능한 서버라면 네트워크 쪽을 먼저 해야 한다 - GPU 설정이 틀리면 서비스가 안 뜨는 데서 끝나지만, **네트워크 이름이 어긋나면 서버에 접속하기 위해 하드웨어 변경을 다시 복원하거나 최악의 경우 OS 재설치가 필요할 수도 있다.**

※ 일부 메인보드와 CPU 조합에는 D-Sub나 HDMI 같은 영상 출력 단자가 아예 없다. **이런 구성에서는 다음 상황이 생길 수 있다.**

그래픽카드를 꽂고 OS를 설치하면 네트워크가 정상 작동한다. 설치를 마치고 그래픽카드를 빼면 **위 문제로 SSH가 끊기는데, 화면 출력이 없어 원인 파악도 불가능하다.** 그런데 확인하려고 그래픽카드를 다시 꽂으면 **PCI 열거 순서가 원래대로 돌아와 모든 것이 정상이 된다.**

**증상이 카드를 뺐을 때만 나타나므로 추적이 대단히 어렵다.** IPMI가 있거나 유사한 경험이 있지 않다면 해결에 오래 걸릴 수 있다.

## 2. 워커 확장을 전제로 짠다

물리적으로 GPU 개수가 바뀌는 경우 외에도, **작업에 할당하는 GPU 수를 조정하고 싶을 때**가 생긴다. 그때마다 코드를 갈아엎지 않으려면 미리 모듈화해 두어야 한다.

| 원칙 | 이유 |
|---|---|
| 워커 수를 상수로 가정하지 않는다 | 목록 길이로만 결정 |
| 워커가 동질하다고 가정하지 않는다 | 성능/VRAM/아키텍처가 다를 수 있음 |
| 인코더는 항상 1벌 | 분리의 전제 |
| **작업 단위를 최소화한다** | 불균형이 1작업으로 제한 + [사람 평가와 중첩](03-pipeline-throughput.md) |

마지막 항목이 실무적으로 가장 효과적이다. **1장 = 1작업으로 쪼개면 정적 라운드로빈으로도 충분하다.** 배치로 묶어 미리 나누면 느린 워커가 전체를 지연시키지만, 1장 단위면 불균형이 최대 1장(약 27초)이다. 이기종 워커가 실제로 생기기 전까지는 동적 디스패처가 불필요하다.

## 3. N이 커질 때 병목이 이동하는 순서

| 순위 | 병목 | 시점 | 대응 |
|---|---|---|---|
| 1 | 워커 기동 시 디스크 I/O | N>=4 | 모델 12GB를 N개가 동시에 읽음. 순차 기동 |
| 2 | 인코더 직렬화 | 다중 사용자 | 사용자 1명이면 프롬프트당 1회라 무관 |
| 3 | 조건 텐서 전송 | 원격 워커 | ID 캐싱 |

1번은 [No.2 4장](02-encoder-separation.md#4-이익-3---워커를-늘려도-인코더는-1벌이다)에서 인코더 2벌만으로도 로드 시간이 2.9배가 된 것과 같은 원인이다. **워커를 늘릴 때 가장 먼저 부딪히는 벽은 연산이 아니라 스토리지다.**

## 4. 기동 인자가 정말 전역 상태인지 의심할 것

이 프로젝트에서 이미지 생성 시 쓰는 **[PuLID](https://github.com/ToTheBeginning/PuLID) ID 임베딩**은 원래 캐릭터를 바꿀 때마다 워커를 전부 재기동해야 하는 것으로 가정했다. 구조상 기동 인자로 넘기게 되어 있었기 때문이다.

그러나 이어진 확인 과정에서 **엔진 내부에서는 처음부터 요청별 파라미터**였고, 단지 HTTP로 넘길 통로가 없었을 뿐이었다. 코드에 두 줄을 추가하자 재기동의 필요성이 사라졌다.

**워커 수 N이 커질수록 재기동 비용은 N배가 된다.** 확장을 전제한 설계에서는 이런 항목을 미리 찾아내는 것이 중요하다.

## 5. 프로세스 종료를 신뢰하지 말 것

이 프로젝트에서 여러 번 경험한 문제다. 상세는 [함정 모음 - 프로세스 관리](99-pitfalls.md#4-프로세스-관리)에 있다. 요점만 옮긴다.

- **`terminate()` 후 짧게 기다리고 끝내면 안 된다.** 모델 로딩 중인 프로세스는 SIGTERM을 늦게 처리한다. 타임아웃 후 `kill()` 폴백이 필요하다
- **기동 요청을 직렬화해야 한다.** 기동 중인 프로세스를 "안 떠 있음"으로 판정하면 중복 세트가 뜬다
- **`pgrep -f` / `pkill -f` 를 셸을 거쳐 실행하지 말 것.** 래퍼 셸의 명령줄에 검색어가 들어 있어 자기 자신을 매칭한다
