## 1. 실험 설계

### 답하려는 질문

> **LLM용 32GB 카드는 이미 있다. 이미지 생성을 위해 추가로 무엇을 살 것인가?**

LLM에 32GB 카드 한 장을 할당하는 것은 고정 조건이다. 그 위에서 이미지 생성용으로 **32GB 한 장을 더 사는 것**과 **더 싼 카드를 조합하는 것** 중 무엇이 나은지를 본다.

### 검증하려는 주장

> 고비용 카드 1장보다 저비용 카드 혼합으로 **동일 비용에서 산출량을 늘리거나 동일 산출량에서 비용을 절감할 수 있다.**

### 측정 조건

```
모델      FLUX D Q8 (DiT) + T5-XXL q8_0 + CLIP-L + VAE
해상도    768 x 768
스텝      15, euler, txt_cfg 1.0, distilled_guidance 3.5
확장      PuLID 활성 (id_weight 0.5)
프롬프트  실사용 길이 512토큰 (2청크)   <- 조건 파일 크기 8,391,936 B 로 검증
시드      고정 (조건 1은 단일 시드 + batch_count, 그 외는 SEED+i)
VAE       타일링 활성
```

```
콜드 스타트   sd-server 전체 종료 -> sync -> drop_caches=3 -> 1초 대기
타이머 시작   서비스 기동이 아니라 첫 요청 시점
              (sd-server 는 가중치를 lazy 로드하므로 모델 로딩이 요청 시간에 포함된다)
반복          각 조합 3회, 중앙값 사용
동시 부하     없음. LLM 서버를 포함한 다른 모든 서비스 정지
```

### 측정 항목

| 항목 | 정의 |
|---|---|
| **1장** | 콜드 상태에서 "1장 생성" 명령 1회 -> 완료까지 |
| **8장** | 콜드 상태에서 "8장 생성" 명령 1회 -> 전부 완료까지 |
| **첫 장** | 8장 명령 중 첫 이미지가 완성된 시점 |

> **8장은 "1장을 만든 뒤 7장을 더 만든" 값이 아니다.** 명령 한 번으로 8장을 요청했을 때의 총 소요다. 실제 사용 패턴과 일치시키기 위해서다.

### 기준선 조건을 명시하는 이유

이 프로젝트에서는 "8장 124초"라는 초기 수치를 한동안 인용하다가, 그것이 **PuLID를 켜기 전** 값임을 뒤늦게 발견했다. PuLID는 스텝당 22%(1.39 -> 1.70 s/it)를 더 쓴다. **잘못된 기준선은 개선을 과소평가하거나 없는 퇴보를 만들어낸다.**

위 실측은 전부 PuLID 활성으로 통일했다. 본문의 장당 시간(26.9초)도 같은 기준이다.

> 이 실험 이전의 실사용 구성(LLM 동시 가동, 인코더 fp16)에서 관측한 값은 8장 기준 145초 -> 132초 -> 108초였다. **격리 조건이 아니므로 아래 표와 같은 축에 놓고 비교하면 안 된다.**

## 4. 파생 계산

### 4-1. 중앙값 정리

| 조건 | 비용 | 워커 | 1장 | 8장 | 첫 장 | 라운드당 |
|---|---|---|---|---|---|---|
| 1 | 700 | 1 | 46.51초 | 261.74초 | 261.54초 | 30.75초 |
| 2 | 230 | 1 | 65.09초 | 256.08초 | 64.80초 | 27.28초 |
| 3 | 215 | 1 | 48.18초 | 240.70초 | 48.00초 | 27.50초 |
| 4 | 415 | 2 | 48.18초 | 134.01초 | 48.09초 | 28.61초 |
| *5* | *615* | *3* | - | *105~107초* | - | *산출값* |
| 6 | 715 | 2 | 49.93초 | 296.36초 | 88.02초 | 82.14초 |
| 7 | - | 1 | 49.69초 | 265.12초 | 49.91초 | 30.78초 |

```
라운드당 = (8장 - 1장) / (ceil(8 / 워커수) - 1)
```

워커 1개면 장당 생성 시간과 같고, 워커 2개면 두 장을 동시에 만드는 한 라운드의 시간이다.

### 4-2. 조건 5 산출

워커 수만 다른 조건 3/4에서 고정 구간과 장당 생성 시간을 역산한다.

```
t(N) = S + ceil(8/N) x a        S = 기동 + 인코딩 (고정),  a = 장당 생성

조건 3 (워커 1) : t3 = S + 8a = 240.70
조건 4 (워커 2) : t4 = S + 4a = 134.01
  -> a = (t3 - t4) / 4 = 26.67초
     S = t4 - 4a        = 27.33초
조건 5 (워커 3) : t5 = S + 3a = 107.3초        (ceil(8/3) = 3 라운드)
```

첫 장 실측(48.1초)을 고정점으로 삼는 다른 방법으로는 이렇게 나온다.

```
t5 = 48.1 + 2 x 28.61 = 105.4초
```

**두 방법이 105~107초로 수렴하므로 그 범위를 쓴다.**

**이 값은 낙관적 상한이다.** 실제로는 두 가지 이유로 더 느릴 가능성이 높다.

- **기동 시 디스크 I/O 경합** - 12GB 모델을 3개 프로세스가 동시에 읽으면 S가 늘어난다. 조건 6에서 워커가 2벌이 되자 첫 장이 49.9 -> 88.0초로 76% 늘었다
- **카드 간 발열 상호작용** - 조건 4를 돌 때 유휴였던 카드가 조건 5에서는 함께 가열된다 (9장)

## 5. 해석 - 축 A: 동일 산출량에서 비용 절감

```
조건 1   700 USD   261.7초
조건 3   215 USD   240.7초
```

**조건 3은 조건 1과 동등한 산출량을 69% 낮은 비용으로 냈다.**

실측에서는 조건 3이 21초(8%) 빨랐다. 다만 **이 차이는 인코더 분리의 효과가 아니라 32GB 카드의 발열 스로틀에서 비롯된 것**이므로 이득으로 계상하지 않는다. 근거는 9장에 있다.

카드 냉각이 동등했다면 두 조건의 8장 소요는 거의 같았을 것이다. **주장은 "더 빠르다"가 아니라 "같은 일을 3분의 1 값에 한다"이다.**

### 이 결과가 성립하기 위한 선행 조건

200 USD짜리 16GB 카드는 **모델이 안 들어가서 애초에 후보가 아니었다.**

| | VRAM 요구 |
|---|---|
| FLUX D Q8 통째로 | 19.1GB -> 16GB 카드 불가 |
| 인코더 분리 후 워커 | **13.6GB** -> 16GB 카드 가능 |

[모듈 분리](02-encoder-separation.md)로 요구 VRAM 하한을 낮춘 뒤에야 이 비교가 가능해졌다. **카드를 고르는 문제로 보이지만 실제로는 작업을 나누는 문제였다.**

## 6. 해석 - 축 B: 동일 비용에서 산출량 증가

```
조건 1   700 USD   261.7초
조건 4   415 USD   134.0초    <- 41% 싸고 1.95배            (실측)
조건 5   615 USD   약 106초   <- 12% 싸고 2.47배            (산출값)
```

**조건 4는 실측만으로 결론을 낸다.** 700 USD짜리 카드 한 장 대신 200 USD짜리 카드 두 장 + 15 USD짜리 인코더를 쓰면, 비용이 41% 내려가면서 처리량이 두 배가 된다.

### 반론 검증 - 워커를 늘린 덕분 아닌가

"카드를 나눈 게 아니라 워커를 두 벌로 늘린 것이 이득 아니냐"는 반론이 가능하다. **조건 6이 이를 검증한다.** 32GB 카드 **한 장**에 워커 2벌(13.6 x 2 = 27.2GB)을 올린 구성이다.

| | 카드 | 워커 | 8장 | 첫 장 |
|---|---|---|---|---|
| 조건 6 | 32GB **1장** | 2 | **296.4초** | 88.0초 |
| 조건 4 | 16GB **2장** | 2 | **134.0초** | 48.1초 |

**워커 수가 같은데 42% 싼 구성이 2.21배 빠르다.** 차이는 카드를 나눴느냐 한 장에 몰았느냐뿐이므로, **이득의 출처는 워커 수가 아니라 물리적으로 분리된 연산 유닛이다.**

### 조건 6은 워커 1벌보다도 느리다

```
조건 7   32GB 1장, 워커 1벌   265.1초
조건 6   32GB 1장, 워커 2벌   296.4초    <- 11.8% 느려짐
```

OOM은 나지 않았다. 27.2GB가 32GB 안에 들어갔고 워커 로그에도 할당 실패가 없다. 그런데도 **이득이 없는 정도가 아니라 순손해**다. 원인은 둘이다.

| 원인 | 근거 |
|---|---|
| **연산 유닛 시분할** | 두 프로세스가 같은 SM을 나눠 쓴다 |
| **기동 시 디스크 경합** | 첫 장이 49.9 -> 88.0초로 **76% 증가**. 12GB 모델을 동시에 읽는다 |

라운드당으로 보면 82.14초인데, 단순 시분할이라면 `2 x 30.78 = 61.6초` 여야 한다. **20초가 더 든 것이 경합의 실제 비용이다.**

> **VRAM에 들어간다는 것과 성능이 나온다는 것은 별개다.** 산출량을 늘리려면 물리적으로 다른 연산 유닛이 필요하고, 그 연산 유닛은 쌀수록 좋다.

## 7. 해석 - 인코더 위치가 미치는 영향

조건 2와 조건 3은 **인코더를 RAM에 두느냐 P104에 두느냐만** 다르다. 워커 카드도 작업 단위도 같다.

| | 조건 2 (RAM) | 조건 3 (P104) | 차 |
|---|---|---|---|
| 첫 장 | 64.80초 | 48.00초 | **16.80초** |
| 8장 | 256.08초 | 240.70초 | **15.38초** |
| **라운드당** | **27.28초** | **27.50초** | **~= 0** |

**16.8초의 격차가 첫 장에서 발생한 뒤 그대로 유지되고, 장당 비용에는 전혀 반영되지 않는다.**

이것이 [인코더 분리 설계](02-encoder-separation.md)의 핵심 전제 - **인코딩을 1회만 하고 결과를 재사용한다** - 가 실제로 작동한다는 직접 증거다. 인코더가 느리면 첫 장이 늦어질 뿐, 이후 장수에는 영향이 없다.

### 파생 - 인코딩 시간은 청크 수에 완전히 선형이다

전용 측정(7-3)에서 양쪽 모두 선형임이 확인됐다.

| | 256토큰 | 512토큰 | 배율 |
|---|---|---|---|
| CPU (16스레드, 격리) | 8.30초 | 16.51초 | **1.99** |
| P104-100 (격리) | 0.33초 | **0.66초** | **2.00** |

sd.cpp는 256토큰 단위로 끊어 처리하므로 **청크마다 가중치를 다시 읽고 연산도 그만큼 늘어난다.** 청크당 고정 비용은 없다.

> 실사용 로그의 P104 인코딩은 0.86초였다. 격리 측정이 정확히 0.66초이므로 **차이 0.2초는 청크당 고정 비용이 아니라 시스템 경합**이다. 초기 문서에서 이를 "청크당 오버헤드"로 적었던 것은 오류였다.

### 파생 - 첫 장 지연과 실제 인코딩 시간은 다르다

조건 2와 3의 첫 장 차이는 16.8초인데, 인코딩 시간의 실제 차이는 `16.51 - 0.66 = 15.85초` 다. 나머지는 이렇게 설명된다.

```
인코더와 워커는 동시에 기동한다
  조건 2   CPU 가 인코딩하는 동안 워커는 DiT 12GB 를 로드한다
  조건 3   P104 인코딩이 0.66초에 끝나도 워커 로드(11.3초)를 기다려야 한다

-> CPU 인코딩 중 일부가 워커 로드 뒤에 숨는다
```

**사용자가 체감하는 지연은 인코딩 시간보다 짧다.** 병렬 기동만으로 일부가 상쇄되기 때문이다.

### 7-2. 카드별 인코딩 성능 - 격리 실측

위 조건 1~7과 별개로, **텍스트 인코더만 단독 기동해 카드끼리 비교한** 측정이다. 카드 간 비교는 조건을 맞춘 격리 측정으로만 의미가 있다.

```
1. 다른 서비스를 전부 정지한다 (워커/LLM 포함)
2. 인코더만 단독 기동
3. 동일 프롬프트로 3회 요청
4. 1회차는 버리고 2/3회차를 쓴다   <- 1회차에는 가중치 로드가 섞인다
5. 카드를 바꿔 반복
```

**결과** (T5 Q8, 256토큰 동일 프롬프트)

| 구간 | V100 16GB | P104-100 | 비 |
|---|---|---|---|
| T5 로드 (디스크 read) | 1.81초 | 0.15초 | ※ 페이지 캐시 영향 |
| T5 로드 (VRAM 전송) | 0.58초 | **5.88초** | 10.1배 |
| **1회차 인코딩** | 3.22초 | 7.31초 | 2.3배 |
| **웜 인코딩 (2/3회차)** | **0.085초** | **0.33초** | **3.9배** |

이 값이 [단위 성능당 가격](00-method.md#4-단위-성능당-가격) 계산의 근거다.

걸러야 했던 것 둘:

- **디스크 read 시간의 역전은 카드와 무관하다.** V100 테스트를 먼저 돌려 디스크에서 읽었고, P104는 페이지 캐시에 올라온 파일을 읽었을 뿐이다
- **1회차끼리 비교하면 배율이 왜곡된다.** 2.3배로 보이지만 실제 연산 성능비는 3.9배다

> **P104가 모듈 단위로 3.9배 느리지만, 8장 생성이라는 시스템 총 소요에서 그 차이는 1% 미만이다.** 3.9배라는 숫자만 보고 185 USD를 더 쓰는 것은 계산을 하지 않은 결정이다.

### 7-3. 왜 CPU 대비 25배인가 - 연산 강도와 분기점

**"인코더를 GPU로 옮기니 빨라졌다"로 끝내면 다른 사람이 자기 장비로 판단할 수 없다.** 기전을 계산으로 분해했다.

#### 측정 - CPU 스레드 스케일링

전용 스크립트([`bench/thread_scaling.py`](../../bench/thread_scaling.py))로 스레드 수를 바꿔 가며 쟀다. 조건 파일 캐시를 매번 제거하고, 모델 로드가 섞이는 1회차를 버렸다.

| 구성 | 256토큰 | 512토큰 | GOPS | 1스레드 대비 | 병렬 효율 |
|---|---|---|---|---|---|
| CPU 1스레드 | 69.52초 | 138.16초 | 35 | 1.00배 | 100% |
| CPU 2스레드 | 37.53초 | 74.26초 | 64 | 1.85배 | 92.6% |
| CPU 4스레드 | 19.79초 | 39.33초 | 122 | 3.51배 | 87.8% |
| CPU 8스레드 | 10.14초 | 20.12초 | 237 | 6.86배 | 85.7% |
| **CPU 16스레드 (SMT)** | **8.30초** | **16.51초** | **290** | **8.38배** | - |
| CPU 기본값 (`-t` 미지정) | 10.09초 | 20.05초 | 238 | 6.89배 | - |
| **P104-100** | **0.33초** | **0.66초** | **7,292** | **210.7배** | - |

**CPU 쪽은 최선의 설정(16스레드) 값을 기준으로 삼는다.** 논지가 "최선의 CPU도 못 따라잡는다"이므로 CPU에 유리한 값을 써야 한다.

```
격차   256토큰  8.30 / 0.33  = 25.2배
       512토큰 16.51 / 0.66  = 25.0배      <- 프롬프트 길이와 무관
```

#### 연산 강도

```
연산량   = 2 x 4.7e9 (T5-XXL 인코더 파라미터) x 256토큰 = 2,406 GFLOP
메모리   = 가중치 Q8 4.83 GB 를 1회 읽음

연산 강도 = 2,406 / 4.83 = 498 FLOP/byte
```

청크 단위로 처리하므로 **토큰이 늘어도 강도는 498로 일정**하다. 위 표의 완전한 선형성이 이를 뒷받침한다.

> 파라미터 수를 4.55e9로 잡거나 활성화 트래픽까지 넣으면 400~500 범위로 움직이지만, 아래 판정은 바뀌지 않는다.

#### 분기점

`분기점 = 연산 성능 / 메모리 대역폭`. P104-100의 대역폭은 320 GB/s다.

| 연산 경로 | 성능 | 분기점 | |
|---|---|---|---|
| **INT8 DP4A** | 22 TOPS | **68.8** | q8_0 이 타는 경로 |
| FP32 | 6.1 TFLOPS | 19.1 | |
| FP16 | 0.095 TFLOPS | 0.30 | **1/64 봉인 - 단, 이 경로는 선택되지 않았다 (12장)** |

```
연산 강도 498  대  분기점 68.8   ->  7.2배   ->  명확한 연산 바운드
```

실측 유효 성능(7,292 GOPS)으로 계산한 유효 분기점 22.8로 재도 21.8배다. **어떤 기준으로도 연산 바운드**라 결론이 견고하다.

#### 이것이 왜 결정적인가

P104의 대역폭 320 GB/s는 **V100의 3분의 1** 수준이다. 메모리 바운드 작업이었다면 이 카드는 참패한다. 실제로 가중치 읽기는 15ms로 전체 330ms의 4.6%에 불과하다.

> **P104가 이 자리에 맞는 이유는 두 조건이 동시에 성립하기 때문이다.**
> No.1 약한 대역폭이 병목이 되지 않는 작업이고, No.2 그 카드의 INT8 연산이 살아 있다.
> **둘 중 하나만 어긋나도 성립하지 않는다.**

**이 카드를 쓸 수 있게 만든 것은 카드 선택이 아니라 q8_0 양자화다.** 다만 그 이유는 속도가 아니라 **적재**였다 - T5-XXL fp16은 9.79GB로 8GB 카드에 애초에 들어가지 않는다. 속도 면에서 q8_0은 f16 대비 2.17배로, 스펙에서 추론했던 것보다 훨씬 작은 폭이다 (12장) -> [No.1 4-1](01-role-assignment.md#4-1-접근은-두-방향이다)

#### 교차 검증

별개 경로로 얻은 두 수치가 맞아떨어진다.

```
V100 웜 인코딩 0.085초  ->  28,306 GOPS   (텐서 FP16 125 TFLOPS 의 22.6%)
P104 웜 인코딩 0.33초   ->   7,292 GOPS   (INT8 22 TOPS 의 33.1%)

비  28,306 / 7,292 = 3.88배
```

7-2의 격리 실측에서 얻은 **"V100 대비 3.9배"** 와 일치한다.

#### SMT가 22% 이득이었다 - 예상과 반대

연산 바운드 SIMD 작업에서 SMT는 통상 손해다. 실행 유닛을 나눠 쓰기만 하기 때문이다. **그런데 물리 8코어(10.14초)보다 논리 16스레드(8.30초)가 22% 빨랐다.**

Zen 2에는 AVX512-VNNI가 없어 ggml의 int8 경로가 `maddubs -> madd -> 누산` 의존 사슬을 탄다. **그 사이의 파이프라인 버블을 SMT가 채운 것**으로 보인다.

> **"연산 바운드"라고 해서 실행 유닛이 포화된 것은 아니다.** 루프라인 판정은 어느 자원이 상한인지를 말할 뿐, 그 자원의 활용률까지 보장하지 않는다. -> [함정 모음 - 연산 바운드라고 SMT를 끄지 말 것](99-pitfalls.md#연산-바운드라고-smt를-끄지-말-것)

참고로 sd-server의 `-t` 기본값은 **물리 코어 수(8)** 였다. 기본값을 그대로 쓰면 22%를 놓친다.

#### CPU를 늘려서 따라잡을 수 있는가

물리 코어당 `290 / 8 = 36.2 GOPS` 다. 같은 세대(EPYC Rome) 전 라인업을 코어 수와 베이스 클럭으로 환산했다.

| 모델 | 코어 | 베이스 | 추정 GOPS | P104 대비 | 중고가 |
|---|---|---|---|---|---|
| 7232P *(이 서버)* | 8 | 3.1 | 290 | 4.0% | $30-60 |
| 7402P | 24 | 2.8 | 786 | 10.8% | $48-90 |
| 7702P | 64 | 2.0 | 1,497 | 20.5% | $600-1,200 |
| 7H12 | 64 | 2.6 | 1,946 | 26.7% | 중고 희귀 |
| **2 x 7H12 (듀얼 소켓 128코어)** | 128 | 2.6 | **3,892** | **53.4%** | - |

**Rome 최상위를 듀얼 소켓으로 꽉 채워도 15 USD짜리 카드 한 장의 절반 남짓이다.** Rome은 2소켓이 상한이므로 **한 대의 기계로는 도달할 수 없다.**

굳이 맞추려면 GOPS당 가격이 가장 싼 7402P 기준 **10개 = 듀얼 소켓 5대**가 필요하다.

| | 비용 | 전력 |
|---|---|---|
| CPU 칩값만 | 약 $480 | - |
| 시스템 전체 (보드/RAM/전원 포함 5대) | **약 $3,500** | **1,800W** |
| **P104-100** | **$15** | **180W** |

**약 230배 / 전력 10배**이며, 그마저도 **분산 인코딩을 지원하는 소프트웨어가 있다는 가정**이다. 실제로는 없다.

위 환산은 8코어 측정을 코어 수/클럭으로 선형 확장한 **추정치**이며, NUMA/CCD 경계의 손실을 반영하지 않아 **CPU 쪽에 유리하다.** 실제 격차는 이보다 크다. 보드/RAM 가격도 개략값이다.

#### 초기 측정치와의 불일치

이 프로젝트의 초기 문서에는 CPU 인코딩이 **13.97초**(256토큰)로 적혀 있었다. 통제된 재측정에서는 같은 기본 설정으로 **10.09초**가 나왔다.

**차이의 원인은 특정하지 못했다.** 재측정 프로토콜은 세 가지가 달랐다 - 워밍 1회 폐기, 조건 파일 캐시 제거, 다른 서비스 완전 정지. **첫 번째가 가장 유력하지만 확인하지 않았다.**

더 엄격한 조건에서 잰 값을 채택했다.

### 7-4. 인코더를 N벌 띄우면 - 운영 관측치

인코더 분리를 도입하기 전, 워커를 늘리면 인코더도 함께 늘어나던 시기의 관측치다.

| | 인코더 1벌 | 인코더 2벌 동시 | 배율 |
|---|---|---|---|
| CPU 인코딩 소요 | 17.7초 | **33~37초** | 1.9~2.1배 |
| RAM 소비 | 9.2GB | **18.4GB** | 2.0배 (선형) |
| **기동 시 모델 로드** | 7.32초 | **21.03초** | **2.9배** |

**이 표는 통제된 A/B가 아니다.** T5를 fp16으로 RAM에 올리던 시기의 실사용 관측치이며(실사용 프롬프트, 다른 서비스 가동 중), 위 조건 1~7과 같은 축에 놓고 비교하면 안 된다. **배율의 방향을 보는 용도로만 쓸 것.**

세 번째 항목이 간과되기 쉽다. **CPU만 경합하는 게 아니라 스토리지도 경합한다.** 같은 가중치 파일을 두 프로세스가 동시에 읽으면서 로드 시간이 2.9배가 됐다. 이 서버는 NVMe라 이 정도였고, **랜덤 4K read 성능이 낮은 SATA SSD나 HDD였다면 격차가 더 컸을 것이다.**

같은 현상이 통제된 조건에서도 재현됐다 - 조건 6에서 워커가 2벌이 되자 **첫 장이 49.9 -> 88.0초로 76% 늘었다**(6장). 워커가 많은 구성을 계획한다면 반드시 계산에 넣어야 한다.

## 8. 해석 - 작업을 쪼개는 비용

N장을 배치로 묶지 않고 N개의 독립 작업으로 돌리면 **작업당 고정 오버헤드가 N번 발생한다.** 얼마인지 모른 채로 "손해가 없다"고 말해서는 안 되므로 측정했다.

**같은 GPU(V100 32GB), 같은 워커 1개**로 배치와 개별 작업만 바꾼 두 조건을 비교한다.

| | 작업 단위 | 인코더 | 8장 | **라운드당** |
|---|---|---|---|---|
| 조건 1 | `batch_count=8` 한 덩어리 | 같은 카드 | 261.74초 | 30.75초 |
| 조건 7 | 1장 = 1작업 x 8 | P104 | 265.12초 | **30.78초** |

**장당 차이가 0.03초다. 사실상 0이다.**

8장 총 소요의 3.4초 차이는 쪼개기 비용이 아니라 **인코더를 별도 카드에 둔 기동 비용**이다. 조건 7의 인코더는 PCIe x4 Gen1에 물린 P104라 T5 가중치를 올리는 데 5.88초가 걸린다. 1장 측정에서 이미 3.2초(46.51 -> 49.69)가 벌어져 있고 그것이 8장에서도 그대로 유지될 뿐, 장당 비용에는 반영되지 않는다.

> 이 결과는 [No.3 조기 표시](03-pipeline-throughput.md)의 전제를 뒷받침한다. **작업을 쪼개는 데 사실상 비용이 들지 않으므로, 사람 평가 시간 `(N-1) x T` 를 공짜로 회수한다.** 조건 텐서를 공유하지 않고 장마다 재인코딩을 해도 마찬가지였다(아래 조건 8, 장당 0.17초). **다만 인코딩이 CPU에 있으면 장당 8.30초가 되어 성립하지 않는다.**

### 첫 장 표시 - 통제 실험 (조건 1 대 조건 8)

앞선 비교(조건 1 대 4)는 표시 방식 외에 **워커 수와 인코더 위치가 함께 달라** 효과를 분리할 수 없었다. 그래서 **독립변인이 표시 방식 하나뿐인 조건 8을 따로 만들어 측정했다.**

| | 조건 1 (배치) | **조건 8 (낱장)** | |
|---|---|---|---|
| 카드 / 인코더 / 워커 | 32GB / 동거 / 1 | **동일** | - |
| **첫 장 (F)** | **261.54초** | **46.68초** | **5.6배** |
| 8장 (G) | 261.74초 | **262.42초** | +0.3% |

**조건 1은 `F ~= G` 다.** 배치는 8장이 전부 끝날 때까지 아무것도 내보내지 않으므로 첫 장 대기가 곧 전체 시간이다.

**낱장으로 쪼개도 8장 총 소요는 0.3%밖에 늘지 않았다.** 장마다 재인코딩을 하는데도 그렇다.

```
조건 8 라운드 1 의 구간 로그

첫 장    get_learned_condition   6.10초   <- 콜드. T5 로드 포함
         sampling               38.18초
         decode_first_stage      1.70초   -> 45.99초

2번째~   get_learned_condition   0.16초   <- 재인코딩 비용
         sampling            26.99 ~ 28.90초
         decode_first_stage      1.5초    -> 28.62 ~ 30.60초
```

**재인코딩이 장당 0.16 ~ 0.18초다.** 7번 더 해도 1.2초라 총 소요에 묻힌다.

> 장당 생성 시간이 28.62초에서 30.60초로 단조 증가한다. 9장의 발열 스로틀이 그대로 재현된 것이다.

**측정 조건** - 조건 1은 2026-08-12, 조건 8은 2026-08-19 측정이며 그 사이 하드웨어와 스택 변경은 없다. 조건 1을 재측정하지 않은 이유는 3회 편차가 0.02초(261.74 / 261.54 / 261.76)로 재현성이 확인됐기 때문이다. 조건 8의 3회는 256.58 / 262.42 / 263.17초이며 중앙값을 썼다.

> **참고 - 실제 최종 구성(조건 4)의 첫 장은 48.09초다.** 조건 8의 46.68초와 비슷하지만 성격이 다르다. 조건 8은 표시 방식 효과만 보려고 만든 진단용이고, 조건 4는 워커 2개와 P104 인코더를 함께 쓴 실제 구매 선택지다.

## 9. 반증 - 32GB 카드가 느렸던 이유

조건 1의 장당 생성이 30.75초로, 조건 3(27.50초)보다 **12% 느렸다.** 원인을 네 가지로 의심하고 하나씩 소거했다.

| 후보 | 검증 방법 | 결과 |
|---|---|---|
| 메모리 대역폭 차이 | 스펙 확인 | X V100은 16/32GB 모두 900 GB/s. 스택 높이(4-Hi/8-Hi)만 다르다 |
| 폼팩터 클럭 차이 | `nvidia-smi` 카드 이름 | X 전 카드가 **SXM2**로 동일 (`clocks.max.sm` 1530 MHz) |
| 배치 경로의 부대 비용 | 로그의 `sampling completed` | X 격차가 전부 sampling **안**에 있었다 |
| 인코더 동거로 인한 VRAM 압박 | **조건 7 추가 측정** | X 아래 |

### 조건 7이 마지막 후보를 소거했다

워커 카드는 그대로 두고 **인코더만 다른 카드로 옮긴** 구성이다.

| | 워커 카드 | 인코더 | 작업 단위 | **웜 sampling** |
|---|---|---|---|---|
| 조건 1 | 32GB | **같은 카드** (19.1GB) | 배치 | **29.15초** |
| 조건 7 | 32GB | **분리** (13.6GB) | 개별 | **29.20초** |
| 조건 3 | 16GB | 분리 (13.6GB) | 개별 | **26.00초** |

**인코더 동거 여부도 배치 여부도 바꿔 봤지만 sampling은 워커 카드만 따라갔다.**

### 원인 - 발열 스로틀

부하 중 클럭과 온도를 재고서야 원인이 나왔다.

```
index, name,                    clocks.sm, clocks.max.sm, power.draw, power.limit, temp
0,     Tesla V100-SXM2-16GB,    135 MHz,   1530 MHz,      26.65 W,    300.00 W,    39
1,     NVIDIA P104-100,         139 MHz,   1911 MHz,       5.32 W,    180.00 W,    32
2,     Tesla V100-SXM2-32GB,   1200 MHz,   1530 MHz,     201.66 W,    300.00 W,    82
3,     Tesla V100-SXM2-16GB,    135 MHz,   1530 MHz,      26.63 W,    300.00 W,    39
```

부하 중 32GB 카드는 **1155~1207 MHz**를 오갔다. 관측된 온도는 **82~83C**.

| 판정 | 근거 |
|---|---|
| **발열 스로틀** O | 부스트의 **78%**. 베이스 클럭(1290 MHz)에도 못 미친다 |
| 전력 캡 X | 300W 한도에 **65~100W 여유**가 남아 있었다 |
| 스펙 차이 X | `clocks.max.sm` 이 1530 MHz로 전 카드 동일 |

`1200 / 1530 = 78%`. 이 카드는 지속 부하에서 부스트 클럭의 4분의 3만 쓴다. 섀시 안에서 더 나쁜 자리에 있었을 뿐이다.

### 왜 콜드에서는 안 보였나

| | 조건 3 (16GB) | 조건 7 (32GB) | 차 |
|---|---|---|---|
| 콜드 첫 sampling | 37.75초 | 39.50초 | +4.6% |
| **웜 sampling** | 26.00초 | 29.20초 | **+12.3%** |

**온도가 쌓이는 데 시간이 걸리기 때문이다.** 정적 스펙 차이라면 첫 장부터 12%여야 한다. **부하가 누적될수록 벌어지는 것이 발열 스로틀의 전형적 신호다.**

### 이 반증이 문서에 미친 영향

12% 격차를 "모듈 분리 덕분"이라고 적었다면, 그 문장은 검증되지 않은 채 남았을 것이고 다른 사람이 같은 구조를 만들어도 재현되지 않았을 것이다. **가설을 소거하는 조건(조건 7)을 추가로 설계하지 않았다면 끝까지 몰랐을 일이다.**

교훈은 [함정 모음](99-pitfalls.md#같은-스펙의-카드라도-지속-성능은-갈린다)에 정리했다.

## 10. 구간 분리 로그

`sd-server` 를 `-v` 로 띄우면 구간별 소요가 분리되어 찍힌다. **총 시간만 기록했다면 위의 반증은 불가능했다.**

### 웜 sampling 비교 (8장 실행, 3회차)

```
조건 1 (32GB, 인코더 동거, 배치)
  38.75  28.45  29.01  29.18  29.15  29.22  29.14  29.23     -> 웜 평균 29.15

조건 7 (32GB, 인코더 분리, 개별)
  39.50  28.44  29.12  29.12  29.32  29.26  29.30  29.32     -> 웜 평균 29.20

조건 3 (16GB, 인코더 분리, 개별)
  37.75  25.71  25.93  26.02  26.05  26.12  26.08  26.10     -> 웜 평균 26.00
```

**첫 장이 모든 조건에서 10초 이상 느리다.** GPU 클럭 램프업 때문이며, 카드와 무관하게 공통으로 나타난다.

### 조건 7의 1장 실행 전문

```
--- 인코더 (P104) ---
loading tensors completed, 0.40s (read 0.12, copy_to_backend 0.18)      <- CLIP-L
loading tensors completed, 6.47s (read 0.60, copy_to_backend 5.50)      <- T5 Q8
sd_encode_conditioning completed, 8.97s

--- 워커 (V100 32GB) ---
get_learned_condition completed, 0.02s                                  <- 조건 주입
loading tensors completed, 11.31s (read 10.21, copy_to_backend 0.46)    <- DiT 12GB
sampling completed, 38.92s
loading tensors completed, 0.20s                                        <- VAE
decode_first_stage completed, 1.59s
generate_image completed in 40.55s
```

읽어야 할 지점 셋:

| 값 | 의미 |
|---|---|
| `get_learned_condition 0.02s` | **조건 텐서 주입 비용이 사실상 0이다.** 인코더 분리 설계의 전제 |
| T5 `copy_to_backend 5.50s` | PCIe x4 Gen1의 대가. **기동 시 1회만 발생** |
| DiT `read 10.21s` | 콜드 스타트로 페이지 캐시를 비웠으므로 디스크에서 읽는다 |

### PCIe 대역폭 참고

| 전송 | 빈도 | V100 (x16 Gen3) | P104 (x4 Gen1) |
|---|---|---|---|
| T5 가중치 5.06GB | 기동 시 1회 | 0.58초 | **5.88초** |
| 실효 전송률 | - | 8.7 GB/s (이론치의 55%) | **0.86 GB/s (이론치의 86%)** |
| 조건 텐서 4.2MB | 요청당 | 0.5ms | 약 5ms |

**기동 시 5.3초를 한 번 더 쓰는 대신 운영 중에는 사실상 0이다.** 8장 생성 240초에서 조건 전송이 차지하는 비중은 요청당 5ms로 8장을 다 합쳐도 0.02% 수준이다.

## 11. 측정하지 않은 것

정직하게 적어 둔다. 아래는 이 실험으로 답할 수 없다.

| 항목 | 이유 | 영향 |
|---|---|---|
| **조건 5 (워커 3)** | V100 16GB를 3장 보유하지 않음 | 산출값이며 낙관적 상한 (4-2) |
| **사람의 평가 시간 T** | 작업/숙련도/피로도에 따라 크게 달라짐 | [No.3](03-pipeline-throughput.md)의 시간 모델은 T를 미지수로 둔 구조 비교 |
| **워밍 상태 성능** | 별도 측정을 수행하지 않음 | 콜드 로그에서 로드/램프업 구간을 빼는 계산으로만 추정 가능 |
| **다중 사용자 동시 요청** | 사용자 1명 기준 | 인코더 직렬화가 병목이 될 수 있다 -> [No.4 3장](04-orchestration.md#3-n이-커질-때-병목이-이동하는-순서) |
| **다른 해상도/스텝 수** | 768x768 / 15스텝 고정 | 해상도가 오르면 잠재 패치 수가 늘어 장당 시간이 비선형으로 증가 |
| **냉각이 균등한 환경** | 이 서버의 32GB 카드가 발열 제약을 받음 | 조건 1/6/7의 값은 냉각이 좋으면 개선될 여지가 있다 (9장) |
| **A100 등 상위 카드와의 직접 비교** | 같은 엔진으로 측정된 공개 자료 없음 | 아래 참조 |

### 11-1. 상위 카드 비교를 넣지 않은 이유

A100 실측치를 이 표에 나란히 놓으려 했으나 **포기했다.** 공개된 A100 수치는 조건이 너무 다르다.

| 변수 | 이 프로젝트 | 공개된 A100 수치 |
|---|---|---|
| 프레임워크 | ggml / stable-diffusion.cpp | PyTorch + diffusers, 상당수가 `torch.compile` |
| 정밀도 | Q8 | bf16 |
| 해상도 | 768^2 (잠재 패치 2,304) | 1024^2 (4,096) |
| 스텝 | 15 | 28 (dev) 또는 4 (schnell) |
| 확장 | PuLID 활성 (+22%) | 없음 |

억지로 정규화하면 겉보기 격차가 **8배 이상**으로 나오는데, **A100의 연산 성능비는 2.5배뿐이다.** 남는 3배 이상은 하드웨어가 아니라 프레임워크/최적화/정밀도 차이다. **표에 나란히 놓으면 A100의 성능을 3배 넘게 과대평가하게 된다.**

> **이 프로젝트도 A100을 클라우드로 대여해 만져 봤다.** 다만 비양자화 모델의 **구동 여부만 확인**했고 성능 측정은 하지 않아, 비교에 쓸 자료가 없다 -> [부록 - 구축 기록](appendix/build-log.md#발단)

> **같은 엔진(ggml)으로 측정된 A100 자료는 확인되지 않았다.** 검색이 부족해서가 아니라 구조적 이유로 보인다 - A100 사용자는 VRAM이 남으므로 양자화할 이유가 없고, 따라서 ggml 대신 PyTorch를 쓴다. **양자화 + ggml 은 VRAM이 부족한 쪽의 조합이다.**

상위 카드와의 비교는 **측정 대신 스펙으로** 했다. 이미지 생성은 연산 바운드이므로 연산 성능비(2.5배)와 가격비(15.7배)만으로 판정이 가능하다 -> [단위 성능당 가격](00-method.md#4-단위-성능당-가격)

**측정할 수 없는 것을 측정한 척하지 않는 편이, 조건이 다른 수치를 나란히 놓는 것보다 낫다.**

## 12. SM 스케일링과 커널 경로 실측

이 장은 **문서를 쓰는 도중에 제기된 두 의문을 검증한 기록**이다. 하나는 "총 처리량을 코어 수로 나눈 평균이 의미가 있는가", 다른 하나는 "P104의 FP16 봉인이 실제로 발동하는가"다. **두 번째 답은 앞선 장들의 서술을 뒤집었다.**

측정 시점 모든 서비스를 내리고 GPU 4장을 유휴 상태로 두었다. 온도 37~44도, SM 클럭 1,530MHz 고정으로 스로틀은 끼지 않았다.

### 12-1. SM 스케일링 - 코어 수와 성능은 선형인가

V100 32GB에서 MPS로 SM 할당 비율을 바꿔 가며 512토큰 인코딩을 쟀다. 지점마다 sd-server를 새로 띄웠고(`CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` 는 클라이언트 기동 시점에만 읽힌다), 1회차는 모델 로드가 섞여 버렸다.

| 설정 | 유효 SM | 인코딩 | 100% 대비 | 선형이라면 |
|---|---|---|---|---|
| MPS 없음 | 80 | 0.199초 | 0.99배 | - |
| MPS 100% | 80 | 0.200초 | 1.00배 | - |
| MPS 50% | 40 | 0.245초 | 1.22배 | 2.00배 |
| MPS 25% | 20 | 0.398초 | 1.99배 | 4.00배 |
| MPS 12.5% | 10 | 0.686초 | 3.43배 | 8.00배 |

**그대로 읽으면 비선형이다.** SM을 1/8로 줄였는데 시간은 3.43배만 늘었다.

#### 고정 비용을 분리하면 선형이다

`시간 = 고정비용 + k/SM` 으로 최소제곱 회귀를 돌리면 이렇게 나온다.

```
고정비용 c = 0.117초
계수    k = 5.67
```

| SM | 실측 | 모델 예측 | 오차 |
|---|---|---|---|
| 80 | 0.200초 | 0.188초 | +6% |
| 40 | 0.245초 | 0.259초 | -5% |
| 20 | 0.398초 | 0.400초 | **-0.5%** |
| 10 | 0.686초 | 0.684초 | **+0.3%** |

**연산 부분은 SM 수에 정확히 반비례한다.** 비선형으로 보였던 것은 SM과 무관한 고정 비용 0.117초가 모든 측정에 얹혀 있었기 때문이다.

그 고정 비용의 정체도 확인된다. 이 측정은 HTTP 왕복과 **조건 gguf 8.39MB를 `/dev/shm` 에 쓰는 시간**을 포함한다.

```
80 SM 연산분(회귀 모델)     0.071 ~ 0.083초
7-2 의 V100 웜 인코딩          0.085초    <- 순수 인코딩 구간
차이                       0.115초  ~=  회귀로 구한 고정비용 0.117초
```

**독립적인 두 경로에서 나온 값이 일치한다.**

> **따라서 "총 처리량 / 코어 수 = 코어당 평균" 은 유효한 지표다.** 코어를 1/8까지 줄이는 동안 효율이 급감하지 않았다.
>
> 다만 **CUDA 코어와 CPU 코어는 구조가 달라 1:1 비교가 성립하지 않는다.** 이 평균값은 [No.2 3장](02-encoder-separation.md#왜-25배인가)에서 **코어 수 240배와 실측 25배의 간극을 설명하는 용도로만** 쓴다.
>
> **한계 -** 이 확인은 V100(Volta)에서 한 것이다. **P104(Pascal)는 MPS의 SM 비율 제한을 지원하지 않아 같은 검증을 할 수 없었다.** MPS의 비율 제한은 SM을 물리적으로 끄는 것이 아니라 할당을 제한하는 것이므로, 클럭과 대역폭은 그대로 남는다는 점도 감안해야 한다.

부수 관측 두 가지. **MPS 자체의 오버헤드는 사실상 0이었다**(MPS 없음 0.199초 대 MPS 100% 0.200초). 그리고 콜드 스타트는 MPS 쪽이 빨랐다(6.12초 대 2.96초).

### 12-2. 커널 경로 - FP16 봉인은 발동하지 않았다

`test-backend-ops perf -o MUL_MAT` 으로 ggml 커널 처리율을 직접 쟀다. 운영 빌드(`build/`, sm_70)와 섞이지 않도록 `build-bench/` 를 `"61;70"` 으로 따로 빌드했다.

#### 실제 인코딩 형상 (GEMM, m=4096 n=512 k=14336)

| | f16 | q8_0 | 우위 |
|---|---|---|---|
| **P104** (Pascal, 텐서코어 없음) | 4.34 TFLOPS | **9.42 TFLOPS** | **q8_0 2.17배** |
| **V100** (Volta, 텐서코어) | **65.71 TFLOPS** | 53.18 TFLOPS | **f16 1.24배** |

이론치 대비로 보면 각 값이 어느 경로를 탔는지 드러난다.

```
P104 f16   4.34 / 6.1 TFLOPS(FP32)     = 71%   -> FP32 경로
P104 q8_0  9.42 / 22 TOPS(INT8)        = 43%   -> DP4A 작동
V100 f16   65.71 / 125 TFLOPS(FP16 TC) = 53%   -> FP16 텐서코어
V100 q8_0  53.18                               -> 역양자화 후 FP16. 그만큼 손해
```

#### LLM 디코딩 형상 (GEMV, n=1)

| | f16 | q8_0 | 우위 |
|---|---|---|---|
| P104 | 294.78 GFLOPS | 432.04 GFLOPS | q8_0 1.47배 |
| V100 | 840.71 GFLOPS | 1.41 TFLOPS | q8_0 1.68배 |

**메모리 바운드 구간이라 읽을 바이트가 절반인 쪽이 이긴다.** 연산 경로와 무관하다.

#### end-to-end 인코딩으로 재도 방향은 같다

커널 벤치는 단일 GEMM 형상만 잰다. **512토큰을 인코더에 통과시킨 총 소요 시간**으로도 확인했다. V100 32GB에 T5를 번갈아 올려 각 5회 측정하고 1회차를 버렸다.

| V100, 512토큰 | 인코딩 | 콜드 스타트 |
|---|---|---|
| q8_0 (5.20 GB) | 0.199초 | **2.98초** |
| **fp16 (9.79 GB)** | **0.169초** | 8.46초 |

**연산은 fp16이 1.18배 빠르다.** 고정 비용 0.117초(12-1)를 빼면 연산분만으로는 0.082초 대 0.052초로 **1.58배**가 되어, 커널 벤치의 1.24배보다 격차가 크다.

**가중치를 절반만 읽는 이점이 연산에서 살아나지 않는 이유는 인코딩이 연산 바운드이기 때문이다**(연산 강도 498). 대신 **기동에서는 q8_0이 2.8배 빠르다** - 9.79GB를 읽어야 하는 차이가 여기서 드러난다.

> **양자화의 이득이 연산이 아니라 적재 쪽에 있다는 것**이 이 표의 요지다. P104에서 q8_0이 필수였던 이유도 속도가 아니라 **8GB에 들어가느냐**였다.

#### 양자화가 유리한지는 카드와 형상의 조합이 정한다

| | GEMV (메모리 바운드) | GEMM (연산 바운드) |
|---|---|---|
| **P104** | q8_0 1.47배 | q8_0 2.17배 |
| **V100** | q8_0 1.68배 | **f16 1.24배** |

**넷 중 하나만 f16이 이긴다.** [No.1 5-1](01-role-assignment.md#5-1-양자화-행렬곱의-세-경로)이 소스 분석으로 추론해 둔 세 경로가 여기서 실측으로 확인됐다.

부수로 나온 값 하나. 같은 형상에서 두 카드의 격차다.

```
f16  기준   65.71 / 4.34  = 15.1배
q8_0 기준   53.18 / 9.42  =  5.6배
```

**양자화가 이종 카드 간 격차를 15.1배에서 5.6배로 좁힌다.** 약한 카드에 일을 맡길 수 있었던 정량적 이유가 여기 있다.

### 12-3. 이 측정이 뒤집은 것

**이 문서는 한때 "P104에서 fp16을 쓰면 약 24초가 걸린다"고 적고 있었다.** 스펙 시트의 "FP16은 FP32의 1/64"를 그대로 곱한 값이었다.

| P104, GEMM 형상 | 스펙 추론 | 실측 |
|---|---|---|
| f16 | 0.095 TFLOPS | **4.34 TFLOPS** |
| 비 | | **45배** |

**봉인은 발동하지 않았다.** ggml은 f16 텐서를 FP16 산술로 계산하지 않는다. Pascal에는 텐서코어가 없어 cuBLAS FP16 경로를 탈 수 없으므로 **f16을 FP32로 변환해 처리한다.** 실측 4.34 TFLOPS가 FP32 이론치의 71%라는 점이 그 증거다.

**24초라는 수치는 근거가 없으므로 문서 전체에서 삭제했다.** 대신 q8_0이 필요했던 이유는 속도가 아니라 **적재**로 정정했다 - T5-XXL fp16은 9.79GB로 8GB 카드에 들어가지 않는다.

> **이 오류는 [No.1 5-2](01-role-assignment.md#5-2-커널-경로는-타이밍으로-단정할-수-없다)가 경고한 함정 그 자체다.** 그 절은 *"커널 경로는 타이밍으로 단정할 수 없다"* 고 썼는데, **스펙으로도 단정할 수 없었다.** 소스를 읽거나 직접 재는 것 외에 방법이 없다.

### 12-4. 재현

## 13. 재현 방법

스크립트는 [`bench/`](../../bench/) 에 있다. GPU UUID와 모델 경로만 바꾸면 된다.

```
nvidia-smi --query-gpu=index,name,uuid --format=csv
```

`bench.py` 상단의 `GPU32` / `GPU16A` / `GPU16B` / `GPUP104` 에 자기 UUID를 넣는다. **인덱스가 아니라 UUID를 쓰는 이유는 [No.4 1장](04-orchestration.md#1-gpu-할당은-반드시-uuid로-지정한다) 참조.**

```
python3 bench.py --condition 3 --count 8 --repeat 3
```

전 조합 무인 실행:

```
nohup python3 bench_all.py > bench/console.log 2>&1 &
```

요약 재출력 (`results.csv` 에서 다시 계산하므로 몇 번이든 가능):

```
python3 bench_all.py --summary
```

**콜드 스타트를 위해 `/proc/sys/vm/drop_caches` 에 쓰므로 root 권한이 필요하다.**

**부하 중 클럭/온도를 반드시 함께 기록할 것.** 별도 터미널에서:

```
nvidia-smi --query-gpu=index,name,clocks.sm,clocks.max.sm,power.draw,power.limit,temperature.gpu --format=csv -l 5
```

9장에서 보듯 이것을 안 재면 **원인을 엉뚱한 곳에 귀속시키게 된다.**
