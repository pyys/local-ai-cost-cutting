# No.2 Encoder Separation - Lowering the Minimum VRAM Requirement

> A record of keeping **only one copy** of an image model's text encoder, separating it from the workers, and launching each on a different GPU.
> **It works with two identical GPUs as well.** It can be read independently of the heterogeneous configuration.
> The target engine is [stable-diffusion.cpp](https://github.com/leejet/stable-diffusion.cpp), and the patches are in [`patches/`](../../patches/).

## 0. What to Check Before Starting (The Gate)

This work **modifies the inside of an inference engine.** The models targeted in this project allowed separation and independent launch, but there is no guarantee another model will. Investigate first, and if you hit a wall, redesign the solution direction entirely.

The items checked here, and their outcomes:

| Check | Why it matters | Outcome |
|---|---|---|
| Is the conditioning a value type | pointers or handles cannot be serialized | O only `vector<T> data + vector<int64> shape` |
| Is conditioning produced in one place | several places means the modification scope explodes | O a single function |
| Is the injection point unambiguous | determines how much plumbing is needed | O a single assignment |
| Is conditioning reused across the whole batch | otherwise separation gains nothing | O outside the batch loop |
| Do other extensions (ID preservation, etc.) touch the conditioning | if they do, separation is impossible | O they do not |
| How many fields are actually populated | fixes what has to be serialized | O **only 2** |

The last item mattered most. The encoder's conditioning struct had more than ten fields, but only **two - the hidden states and the pooled vector - were actually used.** The rest were for other model families. **This differs per model, so verify your own path.**

> The "other extensions" in the fifth item meant [PuLID](https://github.com/ToTheBeginning/PuLID) (face consistency) here. This project needed the same person to appear consistently across images generated by the diffusion workers and was using that extension; running it concurrently did not interfere with module separation.

## 1. The Problem - VRAM Demand of Large Image Models

Putting **every component of a FLUX-family model on one GPU** costs this much.

| Component | Q8 | fp16 |
|---|---|---|
| DiT | 12,125 MB (measured) | ~23,800 MB |
| T5-XXL | 4,826 MB (measured) | 9,084 MB (measured) |
| CLIP-L | 235 MB (measured) | 235 MB (measured) |
| VAE | 160 MB (measured) | 160 MB (measured) |
| Compute buffers + CUDA context | ~1,760 MB | ~1,800 MB |
| **Total** | **~19.1 GB** | **~35 GB** |

Unquantized at fp16, the components including the worker come to about 35GB, which **does not fit even on a 32GB card.** Quantized to Q8 it is still 19.1GB, so **a card with 20GB or more is required.** Smaller models such as SDXL are an alternative, but where the quality difference that comes from model size is decisive, what is needed is **a way to keep the large model while shrinking its memory footprint.**

Fortunately FLUX D, unlike an LLM, **loses little performance when its constituent modules are separated, and the requirements for separating them are comparatively forgiving.**

> Splitting a single module further across several GPUs is far harder and needs a strong interconnect such as NVLink. This project does not cover it -> [No.1 1-3](01-role-assignment.md#1-3-tensor-parallelism-is-a-separate-problem)

**Module separation's primary contribution is not speed but lowering the minimum VRAM requirement.**

The phrasing is deliberate, because **the design flow here is model-first.** This project fixed the model to be used and then chose GPUs to match. Quantization happened along the way, but **the model itself was never swapped.** So the model is fixed and what moves is **"how much does a single card have to have, at minimum, to run this model"** - the minimum VRAM requirement.

Because cards of the same generation get **superlinearly more expensive as VRAM grows**, lowering that minimum even slightly has a large budget effect.

> A V100 32GB and a 16GB differ by 2x in VRAM but roughly 3.5x in price (700 vs 200 USD, South Korean used market, August 2026). The gap widens as capacity grows.

## 2. Gain (1) - The Minimum VRAM Requirement Comes Down

Of the five components in a FLUX-family model, the DiT, VAE, and compute buffers (together, the **worker**) exchange enough traffic that they must share one GPU. T5-XXL and CLIP-L (together, the **encoder**) exchange little with the worker, so separating them costs little performance.

With worker and encoder on one GPU the requirement is 19.1GB, so a card with **20GB or more** is needed. Separated, they become 13.6GB and 5.2GB and fit on **one 16GB card and one 8GB card**. This is the precondition on which [No.1 Role Assignment](01-role-assignment.md) rests.

> **This separation was unnecessary in the first system.** Back then a single V100 32GB carried FLUX whole, with T5 resident in that card's VRAM. **While designing the rebuild, "can it be split-loaded" was confirmed first, and only once that answer was in did a 16GB card become a candidate** -> [Appendix - Build Log](appendix/build-log.md#rebuild-requirements)

The first validation step put **the separated encoder in RAM rather than on a GPU**, just to confirm the idea worked at all. The engine's backend selection assigns the text encoder to the CPU.

```
sd-server --backend te=cpu <all other arguments identical to a normal launch>
```

**This test can be run immediately, with no additional hardware.** At this stage two things were confirmed: the worker's VRAM demand dropped to 13.6GB, and split loading produced identical images.

CPU encoding was slow, though. At 512 tokens it took **16.51 seconds** against **0.085 seconds** for V100 encoding under the same conditions. That figure is from isolated conditions with no other load, and **it gets slower when the CPU is doing anything else** -> [Pitfalls](99-pitfalls.md#8-cpu-bound-work-contaminates-gpu-measurements)

Even with CPU encoding, the designed structure held.

## 3. Gain (2) - The Encoder Goes on a Far Cheaper GPU

The separated encoder has the following properties.

- While producing N images from the same prompt, **the computation is needed only once**
- The computation itself is not large (the "eats memory, does not compute" module from [No.1 Section 3](01-role-assignment.md#3-let-the-nature-of-the-work-choose-the-card))
- After computing, **only the conditioning tensor is transferred**, so traffic is very small (4.2MB per request)

### Choosing a Card to Match q8_0 Quantization

**Quantization was already settled by this stage.** The decision that shrank the whole model from 35GB to 19.1GB was made in Section 1, and at the point of finding a card for the encoder the requirement was simply **"the cheapest card that holds 5.2GB."**

Extrapolating from the compute time observed with the encoder in CPU RAM, it was reasonable to judge that **moving from CPU to GPU would pay off even with a GPU far cheaper than a V100.** Taking the view that it only needed enough VRAM to hold the quantized encoder, a P104-100 with 8GB was bought for **about 15 USD** and tested.

> Note: **quantization does not necessarily help on every axis - memory reads, compute, and so on.** The direction differs by card and by phase. Measurements are in [Appendix 12](98-benchmark.md#12-sm-scaling-and-kernel-path-measurements).

Moving the encoder from RAM to the P104 gave:

| Encoder location | 256 tokens | 512 tokens | Conditions |
|---|---|---|---|
| CPU (RAM, 16 threads) | 8.30s | 16.51s | isolated |
| **P104-100** | **0.33s** | **0.66s** | isolated |

> The 0.86s seen in production logs is this figure plus about 0.2s of system contention -> [Appendix 7-2](98-benchmark.md#7-2-encoding-performance-by-card---isolated-measurement)

### Why 25x

The P104 is 25x faster than the CPU here for these reasons.

**1. The operation benefits from parallelism.** In CPU thread scaling tests, raising thread count 8x made encoding **6.86x faster (85.7% parallel efficiency).** Most of the computation does not depend on the results of other computation.

**2. The P104 offers 240x more parallelism than the CPU.** The CPU has 8 cores; the card has 1,920 CUDA cores. **Per-core performance is higher on the CPU, but the benefit of 240x the core count outweighs the benefit of per-core performance** -> [Appendix 7-3](98-benchmark.md#7-3-why-25x-faster-than-cpu---arithmetic-intensity-and-ridge-point) / [Appendix 12](98-benchmark.md#12-sm-scaling-and-kernel-path-measurements)

**3. It is compute-bound with small traffic.** Encoder computation has an **arithmetic intensity of 498**, 7.2x above the P104's INT8 ridge point (68.8), making it compute-bound; and the **conditioning tensor the encoder hands to the worker is only 4.2MB per request**, so separating the cards does not make transfer the bottleneck.

> Note: because encoding's parallel gain scales nearly linearly, adding CPU cores is inefficient in per-core price terms against a GPU. The arithmetic and the cost conversion are in [Appendix 7-3](98-benchmark.md#7-3-why-25x-faster-than-cpu---arithmetic-intensity-and-ridge-point).

## 4. Gain (3) - Adding Workers Does Not Add Encoders

When producing N images from the same prompt, the simplest way to raise throughput is to run N workers each holding the model. But **that way you end up with N encoders too.**

```
worker A (GPU0) : CLIP-L + T5 + DiT + VAE
worker B (GPU2) : CLIP-L + T5 + DiT + VAE     <- T5 duplicated
```

**N-1 of those encoders occupy VRAM without contributing anything.** During testing and design, with the encoder placed on the CPU and two workers each holding an encoder, resources were wasted on three counts.

| Waste | Observation |
|---|---|
| CPU encoding time | **1.9~2.1x** with two running at once |
| RAM consumption | **linear growth** (per encoder copy) |
| **Model load at startup** | **2.9x** with two running at once |

The third is easy to overlook. **It is not only the CPU that contends - storage does too.** Several processes reading the same weight file at once make loading sharply slower. This server has NVMe, hence 2.9x; **on storage with weaker random 4K read the gap grows.**

Original figures and the limits of the measurement conditions are in [Appendix 7-4](98-benchmark.md#7-4-running-n-encoders---operational-observations).

Separating the encoder into **a single copy** and sharing the computed result (the conditioning tensor) across workers removes this waste.

```
Encoder service (x1)          conditioning tensor gguf     Diffusion workers (xN)
CLIP-L + T5 Q8      ---------------------------------------------------->    DiT + VAE
                      /dev/shm/sdcond-<hash>              (no text encoder)
```

**Combined with the gain from Section 2, the conclusion is this.** Doubling throughput becomes possible with **a 200 USD 16GB GPU** rather than a 700 USD 32GB card.

### What This Structure Buys, Summarized

- **The minimum VRAM requirement drops from 19.1GB to 13.6GB** (-> the cost of adding a worker falls)
- **Encoding cost does not grow as workers are added**
- **The N images are produced one at a time across the workers, so unlike a batch each can be shown to the user the moment it completes** -> [No.3 Pipeline Throughput](03-pipeline-throughput.md)

## 5. Implementation - Serialization Design

The key is **not interpreting** the axis convention (row-major versus ggml's `ne` ordering).

```
round-trip the shape vector and the flat data exactly as they are
```

Assign no meaning and the data is restored exactly whichever convention applies. If the axes get transposed, images break silently and debugging is painful.

ggml's `ggml_n_dims()` **truncates trailing dimensions of size 1.** The original dimension count has to be recorded separately in the KV metadata for the round trip to be exact.

The transfer volume is small. The actual file size matches the theoretical value to the byte.

| Tokens | Calculation | Actual file |
|---|---|---|
| 256 | 4096x256x4 + 768x4 + header | **4,197,632 B** |
| 512 | 4096x512x4 + 768x4 + header | **8,391,936 B** |

`4096 x tokens x 4` is the hidden states, `768 x 4` is the pooled vector, and the remaining 256B is the gguf header. **The arithmetic confirms the file contains exactly two tensors** - which also serves as after-the-fact verification that the Section 0 investigation was right.

**With a distilled model (no CFG needed), uncond is never computed, so only one copy has to be sent.**

> **A diagnostic technique:** token count can be back-calculated from the conditioning file size alone.
> `tokens = (file size - 3328) / 16384`
> Useful for telling whether slow encoding is caused by chunk count or something else.

## 6. Implementation - Verify Through the CLI Before HTTP

Build HTTP first and when an image comes out wrong you **cannot tell whether serialization, injection, or the network is at fault.** Prove it with the CLI first.

```
1) normal generation + save the conditioning     -> image A
2) drop the text encoder arguments, inject only the conditioning  -> image B
3) are A and B identical pixel for pixel
```

That single test proves three things at once.

- the serialization round trip is correct
- the injection point is correct
- **the worker starts without a text encoder at all**

The third had a prior concern - "model metadata validation might reject a missing encoder" - but it passed. Weights are lazily loaded, so **what is never called is never loaded.**

## 7. How the Encoder Service Actually Behaves

The encoder needs a `--diffusion-model` path too, because **the engine picks the conditioner type by looking at the model version.**

But **the weights are not loaded.** Lazy loading means no VRAM is used unless diffusion actually runs.

```
reported estimate : 17346 MB
actually allocated:  5181 MB   (T5 Q8 4826 + CLIP-L 235 + context)
```

The log's "total params memory size" is only an estimate. **Actual allocation has to be checked with `nvidia-smi`.**

## 8. Results

These measurements answer **"what should I buy to make image generation cost-efficient."**

768x768 / 15 steps / PuLID enabled / 512-token prompt, cold start, median of three runs per combination.
**Measurement conditions, raw records, derived calculations, and the disconfirmation process are in [Appendix - Benchmark Raw Data](98-benchmark.md).**

| Condition | Configuration | Added cost | Workers | **8 images** | First image | Throughput |
|---|---|---|---|---|---|---|
| 1 | V100 32GB x1, loaded whole (batch) | 700 | 1 | 261.7s | 261.5s | 1.83 img/min |
| 2 | V100 16GB x1 + encoder in RAM | 230 | 1 | 256.1s | 64.8s | 1.87 img/min |
| **3** | **V100 16GB x1 + encoder on P104** | **215** | 1 | **240.7s** | 48.0s | **1.99 img/min** |
| **4** | **V100 16GB x2 + encoder on P104** | **415** | 2 | **134.0s** | **48.1s** | **3.58 img/min** |
| *5* | *V100 16GB x3 + encoder on P104* | *615* | *3* | *~106s* | - | *~4.53 img/min* |
| 6 | V100 32GB x1 + P104, **two workers** | 715 | 2 | 296.4s | 88.0s | 1.62 img/min |
| *7* | *V100 32GB x1 + P104, one worker (control)* | *715* | *1* | *265.1s* | *49.9s* | *1.81 img/min* |

*Condition 5 is not a measurement but a value back-calculated from conditions 3 and 4, and is an optimistic upper bound -> [Appendix 4-2](98-benchmark.md#4-2-deriving-condition-5)*

*Condition 7 is not a purchase candidate but the control for condition 6. Its hardware is identical to condition 6 and only the worker count differs -> [Appendix 4-1](98-benchmark.md#4-1-median-summary)*

> Why the difference between conditions 2 and 3 shows up only in the first image is in [Notes and Caveats 2)](#notes-and-caveats); why condition 3 being faster than condition 1 was not counted as a gain is in [Notes and Caveats 3)](#notes-and-caveats).

> **Throughput is converted as `8 images / time for 8 images`.** Because the measurements are cold-start, model load time sits in the denominator, so **the figure comes out lower than steady-state throughput under continuous operation.** It is usable as-is for comparing conditions, but do not quote it as an absolute.

### Three Conclusions

**No.1 The same throughput at 69% lower cost** - a 215 USD configuration produces what a 700 USD one does. The precondition that had to hold first is in [Notes and Caveats 1)](#notes-and-caveats).

**No.2 1.95x the throughput at the same cost** - a 415 USD configuration is 41% cheaper than the 700 USD one and produces twice as much.

**No.3 The gain comes from splitting cards, not from worker count** - with the same two workers, putting them on **one** 32GB card gives 296.4s while splitting across **two** 16GB cards gives 134.0s, a **2.21x** difference. Two workers on one card is even slower than one worker (265.1s). **Fitting in VRAM and performing are separate things.**

## Notes and Caveats

**1)** A 200 USD 16GB card **was never a candidate, because the model would not fit.** Only after q8_0 quantization and the module separation in Section 2 brought the single-card requirement down **from 19.1GB to 13.6GB** did it become a GPU usable for FLUX D.

**2)** One thing was confirmed incidentally - **encoder placement affects only the first image, not the per-image cost.** Conditions 2 and 3 differ by 16.8s on the first image but are effectively identical per round, 27.28s against 27.50s. **That is direct evidence that the design premise of encoding once and reusing the result actually works** -> [Appendix 7](98-benchmark.md#7-interpretation---the-effect-of-encoder-placement)

**3)** Condition 3 was 21 seconds (8%) faster than condition 1, but **that difference is not an effect of encoder separation.** It comes from thermal throttling on the 32GB card, so it was not counted as a gain -> [Appendix 9](98-benchmark.md#9-disconfirmation---why-the-32gb-card-was-slower)
